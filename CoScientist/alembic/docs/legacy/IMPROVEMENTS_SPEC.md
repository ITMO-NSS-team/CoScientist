# Alembic — Improvement Spec

Consolidated, deduplicated spec of features alembic could adopt, drawn from the ToolRosella and ToolMaker comparisons ([TOOLROSELLA_COMPARISON.md](./TOOLROSELLA_COMPARISON.md), [TOOLMAKER_COMPARISON.md](./TOOLMAKER_COMPARISON.md)) and alembic's current design ([DESIGN.md](./DESIGN.md)). Goal: maximize **stability/robustness** and produce the metrics a paper needs, **without giving up** alembic's edge (autonomous multi-tool, served MCP, two-venv, real in-loop invocation).

## Validation & correctness

### F1 — Static import/symbol AST gate
**Problem.** The coder can hallucinate function/class names; alembic only catches this at `validate_syntax` (module import) or later via the debugger — expensive.
**Spec.** New deterministic tool `check_symbols(repo_url)` run between coder and validator: AST-scan the cloned repo for public exported symbols per module; AST-parse `server.py` + `helpers/*.py`; flag every `from <mod> import <sym>` (and wrapped call) where `<mod>` is a repo module but `<sym>` isn't exported. Return structured issues; on issues, route back to coder (or debugger Class C) **before** any venv execution.
**Integration.** Add as a tool + a thin gate stage in `main.py` after Coder; reuse `tools/scripts/compat_check.py`-style AST walking.
**Effort.** Low.

### F2 — Semantic output-correctness gate
**Problem.** `invoke_mcp_tool` only reports `{ok: True/False}` (no exception). A tool can run cleanly and return garbage — common for scientific tools.
**Spec.** After a successful `invoke_mcp_tool`, add an LLM judge that checks the **returned value** against the explorer's documented "Returns"/example: is it plausible, and does it have the expected keys/types/shapes? Emit `{successful, reasoning}`. A `False` verdict triggers the debugger just like an exception.
**Integration.** New step in the Validator instruction + a small `assess_output` helper; feed it the sample's expected-output description from the coder's `samples:` block.
**Effort.** Low–Medium.

### F3 — Held-out validation invocation
**Problem.** Alembic validates with the same samples the coder declared, so a tool that hard-codes the demo path/file passes.
**Spec.** Require the explorer/coder to emit, per tool, **two** invocations with *different* real inputs (e.g. a second sample file, different params). Validator must pass **both**; a tool that only passes its own demo args is marked FAILED (overfit).
**Integration.** Extend the coder `samples:` schema to `examples: [primary, holdout]`; Validator Step 4 loops over both.
**Effort.** Medium (depends on repos shipping ≥2 inputs; fall back to param variation).

## Tool selection

### F4 — Bounded, confidence-ranked, AST-verified tool selection
**Problem.** The explorer proposes "1–5 scenarios" via prompt only — uncapped, unverified, signatures guessed.
**Spec.** Deterministic post-processing of explorer output: (a) hard cap on total tools (e.g. ≤12); (b) per-tool confidence tiers with per-tier caps (high→5/med→3/low→1); (c) **intersect** proposed function/class names with the repo's actual AST symbols, dropping `test`/`example`/private; (d) capture each kept symbol's **real parameter names** and pass them into the coder so wrappers use correct argv (pre-empts wrong-kwarg `TypeError`s the debugger currently fixes reactively).
**Integration.** Run between Explorer and Coder; reuse F1's AST symbol scan; thread `function_signatures` into the coder prompt.
**Effort.** Medium.

## Environment & resources

### F5 — First-class conda / `environment.yml` path
**Problem.** Alembic reaches conda only as "Attempt 3"; scientific repos (rdkit, openbabel, pinned CUDA) often need it.
**Spec.** Promote conda + `environment.yml` to a primary environment strategy alongside uv: detect `environment.yml`, honor channels, use `--solver=libmamba`, install conda deps then the pip section. Keep two-venv semantics (conda env = repo venv; server venv stays Py≥3.10 with fastmcp).
**Integration.** Extend `tools/venv.py` (`setup_venv`) + the Environment instruction's decision tree.
**Effort.** Medium.

### F6 — External resource acquisition (weights download, dataset mounts)
**Problem.** Neither alembic nor ToolRosella fetches pretrained weights/models or README-only-mentioned downloads — a dominant failure cause for ML repos.
**Spec.** Add a resource step in the Environment/build phase: (a) the agent may **download model weights** (README-driven, `huggingface-cli`/`wget`/`gdown`, gated by `HF_TOKEN` via F7), recording fetches so they're baked into the image; (b) **datasets/large inputs are NOT baked** — declare them as mount points / sample paths supplied at invocation time. Explorer notes required artifacts in `exploration.md`; Environment acts on "download weights" but defers "needs dataset" to a mount.
**Integration.** New Environment instruction section + allow `bash_env` to run download CLIs; document a `mounts:`/inputs convention for the served container.
**Effort.** Medium–High.

**Implemented 2026-07-07 (weights-download half; dataset-mount convention (b) still deferred — no repo in the current benchmark subset needs it yet).** Driven by the TM-Bench subset (`benchmarks/alembic/toolmaker_subset_nomusk.txt`), specifically `mahmoodlab/UNI` and `mahmoodlab/CONCH` — both gated HuggingFace models (`MahmoodLab/UNI2-h`, `MahmoodLab/conch`) requiring an approved `HF_TOKEN`.
- `instructions/explorer.py`: new Step 4c — while reading the README/code, flag pretrained-weight requirements (`from_pretrained`, `hf_hub_download`, `snapshot_download`, `timm.create_model(..., pretrained=True)`, `hf-hub:` references, gated-access wording) and record the exact HF repo ID, gated status, loading call, and expected local path in a new "External model weights" bullet in `exploration.md`'s Environment Setup section. Explicitly scoped to weights only — datasets are out of scope by instruction.
- `instructions/environment.py`: new Step 4b, run after the compatibility check, before writing the report — installs `huggingface_hub` into the right venv and either pre-warms the HF cache (`hf-hub:` style loads) or downloads to the repo's own expected path (explicit-path style loads, e.g. CONCH's `checkpoints/conch/pytorch_model.bin`), using the `HF_TOKEN` already present in the container's environment (no explicit passing/printing). A 401/403/gated error is treated as an access problem, not a bug — recorded and the stage moves on, not retried or worked around. New "External model weights" section added to `environment.md`'s report template.
- `tools/shell.py`: `bash_env`'s timeout raised 300s → 900s — a multi-GB weight download needs more room than the original "slow pip install" budget assumed.
- **Why pre-warm during Environment, not lazy-load during validation:** F37 (above) caps a single `invoke_mcp_tool` call at 120s. A cold first-time multi-GB download during Step 4 sampling would never finish inside that budget and would be misreported as "too slow" every single run — pre-downloading during Environment's much larger 2400s budget is what makes F37 and F6 work together instead of at cross purposes.
**Not yet live-verified** — next step is a benchmark run against `toolmaker_subset_nomusk.txt` (excludes MUSK, whose HF access is still pending) to confirm UNI/CONCH's weights actually download and get baked into the image.

### F7 — Declared, allowlisted repo-secret injection
**Problem.** Alembic injects only its own LLM keys (and scrubs them); a repo-required runtime secret (HF token, inference API key) has no channel, so token-gated tools can't be built or served.
**Spec.** Support a per-repo `env:` declaration (config/task-level) of required secret names; resolve from host env via an **allowlist** substitution (e.g. `${env:HF_TOKEN}`); inject into build + serve containers; keep them out of the committed image (bake-then-remove, combined with alembic's existing secret scrub). Surface available var names to the agents in prompts.
**Integration.** Extend `start_chain.py` env passthrough + add a substitution util; mention available vars in Environment/Coder instructions.
**Effort.** Low–Medium.

## Reproducibility & isolation

### F8 — Reproducible image from a recorded `install.sh`
**Problem.** Alembic `docker commit`s the mutated build container — opaque, large, hard to audit/reproduce.
**Spec.** Record the Environment agent's **successful** setup commands (venv creation, installs, apt-get, downloads) into an ordered `install.sh` / generated Dockerfile; build the served image with a clean `docker build` from that script instead of committing the dirty container. Keeps the image minimal, reviewable, and deterministically rebuildable.
**Integration.** Log env-agent commands (already partly in `pipeline.log`) into a structured script; swap the commit step in `start_chain.py` for a build step.
**Effort.** Medium.

### F9 — Fresh-checkpoint isolation per validate/debug attempt
**Problem.** Validator/debugger mutate one shared workdir; accumulated side-effects can mask or fabricate failures across iterations.
**Spec.** Freeze the post-install state as a checkpoint (image from F8, or a snapshot of `output/`+venv); before **each** validation/debug attempt, reset the runtime to that checkpoint so every attempt runs against the same clean installed environment. Debug exploration is allowed but discarded; only the code edit persists.
**Integration.** Wrap the Validator loop with a `reset_runtime()` step; pairs naturally with F8.
**Effort.** Medium.

## Agent-loop quality

### F10 — Persistent failure-memory across debug iterations
**Problem.** The debugger is largely stateless per call; alembic only guards with "stop on identical error," allowing oscillating fixes.
**Spec.** Maintain a running list of compact `problem_summaries` (diagnosis + attempted fix) and feed it into each subsequent debug/diagnose prompt ("avoid repeating these"). Use it to detect near-duplicate diagnoses, not just byte-identical errors.
**Integration.** Thread a summaries list through the Validator↔Debugger calls in `main.py`/instructions.
**Effort.** Low.

### F11 — Tiered model routing
**Problem.** One `MODEL` drives every agent; planning/first-implementation benefit from stronger reasoning, the repair loop does not.
**Spec.** Allow per-role model selection: a reasoning model for Explorer planning + initial Coder implementation, a cheaper/faster model for Validator/Debugger iterations. Configurable via env (`MODEL_REASONING`, `MODEL`).
**Integration.** `agents.py` already centralizes `MODEL`; add a second constant and assign per agent.
**Effort.** Low.

## Observability & benchmarking

### F12 — Structured run metrics + error taxonomy
**Problem.** Alembic logs human-readable events but emits no structured per-run metrics or failure classification — exactly the data a paper needs.
**Spec.** Per run, emit a JSON record: per-stage durations, step/tool-call counts, LLM call/token/retry stats, guard/timeout firings, and **every failure classified into a taxonomy** (`ModuleNotFound`/`Import`/`Environment`/`Build`/`Syntax`/`Runtime`/`AttributeError`/`FileNotFound`/…). Aggregate across a benchmark into pass-rate-by-stage and error-distribution tables.
**Integration.** Add a metrics sink alongside the loguru file sink in `main.py`; classify in the Validator/Debugger; aggregate in `run_benchmark.py`.
**Effort.** Low.

**Implemented 2026-07-06.**
- **Classification (`agent_runtime.py`).** `classify_error(text)` maps a raw error/traceback string to one of `ModuleNotFound`/`Import`/`FileNotFound`/`AttributeError`/`KeyError`/`IndexError`/`NameError`/`TypeError`/`ValueError`/`Encoding`/`Syntax`/`Timeout`/`Environment`/`Runtime`/`Unknown`/`Other`, by taking whichever taxonomy needle occurs **last** in the text. This matters because generated `server.py` tool functions wrap the real exception (`raise RuntimeError(f"...: {e.stderr}") from e`), so the wrapper's own class name always appears *before* the wrapped traceback's real exception in the string — "last match wins" recovers the actual root cause (e.g. `ModuleNotFoundError`) instead of the generic `RuntimeError` wrapper. Classification runs inside `_run_agent_once`'s existing event loop, on every `function_response` from `invoke_mcp_tool`/`validate_syntax`/`run_tests` where the tool reports `ok`/`passed` is `False` — no new call sites, no LLM involvement, so it can't add latency or fail independently of the tool call it's classifying.
- **Bonus: F16/F17 visibility.** The debugger's `AgentTool` wrapper (`agents.py`'s `_DebuggerAgentTool`) swallows its own timeout (F16) or exhausted-retry (F17) into a plain text result rather than raising, so those events were previously invisible to any metrics. `_run_agent_once` now recognizes the two fixed strings it returns (`"timed out after"`, `"failed twice"`) and counts them as a `DebuggerTimeout` taxonomy entry — giving F16/F17's firing rate a number for the first time.
- **Per-stage metrics (`agent_runtime.py` → `main.py`).** `run_agent()`'s return type grew from `(final, steps, tokens)` to `(final, steps, tokens, stage_metrics)`, where `stage_metrics = {"tool_calls": {name: count}, "failures_by_class": {label: count}, "guard_retries": int, "transient_fault_retries": int, "abort_reason": "tool_repeat"/"max_steps"/"guard_exhausted"/None}` — aggregated across every guard-retry attempt and F22 fault-retry within the stage. `abort_reason` reflects only the *most recent* `_run_agent_once` call (an earlier attempt's abort is cleared once a later retry finishes clean — see bug fix below), or `"guard_exhausted"` if the guard-retry budget ran out while write_report/venv nudges were still outstanding, overriding a merely-`None` last-attempt status. `main.py`'s `_run_stage()` wraps the call with `time.monotonic()` for wall-clock duration (recorded even on a stage timeout, alongside a `"stage_timeout"` abort reason) and folds everything into `pipeline_metrics`, written to `reports/metrics.json` exactly as before (no schema-breaking rename of the existing `actions_per_stage`/`tokens_per_stage`/`total_actions`/`total_tokens` keys — only new keys added: `durations_per_stage`, `tool_calls_per_stage`, `guard_retries_per_stage`, `transient_fault_retries_per_stage`, `abort_reason_per_stage`, `failures_by_class`).
- **Benchmark-level aggregation (`run_benchmark.py`).** New `aggregate_metrics(records)` rolls every repo's `metrics.json` (already pulled in by `extract_validation()`) into: stage completion counted as `completed/attempted` per stage (a repo only counts as "attempted" a stage if it has a recorded duration, and "completed" if it also has an `actions_per_stage` entry — i.e. didn't time out), and a summed cross-repo `failures_by_class` table. Repos with no `metrics.json` at all (crashed before the `finally` block, or skipped by the pre-flight availability check) are excluded from the denominator rather than counted as stage failures. Appended to `summary.md` as a new `## Aggregate metrics (F12)` section; `summary.json`'s top level changed from a bare list to `{"repos": [...], "aggregate": {...}}` (no other script in the repo consumed the old list-shaped `summary.json`, confirmed by grep before making this change).
- **Two bugs caught by the first live verification attempt, both fixed same-day:**
  1. **`extract_validation()` never read `metrics.json` when `validation.md` was missing.** The function returned early (`{"error": "validation.md not readable", ...}`) the moment the primary report was absent — exactly the case (validator timed out, or was skipped because the coder never produced artefacts) where the richest metrics data exists and matters most. Fixed by always attempting to pull `metrics.json`/`error.json` regardless of whether `validation.md` was readable, merging into whichever base dict (`parse_validation()`'s or the error fallback's) applies. Caught by inspecting a real `biotite` run where `aggregate_metrics()` reported `repos_with_metrics: 0` despite a rich, real `metrics.json` sitting right there in the committed image.
  2. **`abort_reason` accumulated instead of reflecting current state.** The original code only updated `abort_reason` when the current attempt's per-call abort was truthy (`if this_abort: abort_reason = this_abort`), so a stage that aborted once (e.g. `tool_repeat`) and then genuinely succeeded on the next guard-retry attempt would still misreport the stale abort from the failed first attempt. Fixed by unconditionally overwriting `abort_reason` on every attempt (so it always reflects the latest), and by explicitly setting `abort_reason = "guard_exhausted"` when the guard-retry budget runs out with nudges still outstanding (distinct from, and more informative than, whatever the last attempt's own per-call status happened to be — often `None`, since the last attempt can complete with a normal final response and simply never call `write_report`).
- **Testing.** Unit-tested `classify_error()` against 10 cases including two real nested-traceback strings taken verbatim from the `astronomy` rerun5 log (`ModuleNotFoundError` correctly recovered from inside a `RuntimeError` wrapper; `AttributeError` likewise) — all 10 passed. Unit-tested `_tool_outcome()` against all three validation-tool response shapes plus a non-dict guard. Unit-tested `aggregate_metrics()` against a synthetic 4-repo set (one fully-completed, one validator-timeout, one crashed-with-no-`validation`, one unreachable-and-skipped) and asserted the exact expected `stage_completion`/`failures_by_class`/retry totals. ### F22 — Silent provider fault: unmapped `finish_reason: "error"` burns ~4 min per occurrence, uncaught by F17
**Problem.** Found in the rerun3 targeted-verification run (`BioSPPy.log`, 2026-07-06): during the Coder stage, two separate LLM turns ~4 minutes apart each ended with `LiteLLM:WARNING core_helpers.py:107 - Unmapped finish_reason 'error', defaulting to 'stop'`, followed immediately by a stub/non-actionable "final" response (e.g. *"Now I'll implement the MCP server file..."* with no tool call), which then only recovered via `main.py`'s unrelated `write_report`-guard nudge (`MAX_GUARD_RETRIES=3`, i.e. `[guard] Retry 1/3`, `Retry 2/3`). The stage's `server.py` write finally succeeded on the 3rd attempt, one second before the 1500s Coder `STAGE_TIMEOUT` fired — i.e. the fault very nearly cost the whole stage outright, and did cost ~8 of the 25 available minutes plus 2 of 3 guard-retry slots.
**Root cause (confirmed by reading source inside the built image).** `litellm/litellm_core_utils/core_helpers.py`'s `map_finish_reason()` holds an explicit table mapping every provider's finish-reason string to the OpenAI-standard set (`stop`/`length`/`tool_calls`/`content_filter`/`function_call`) — it even has a deliberate `"ERROR": "stop"` entry for a different provider's uppercase variant. The lowercase `"error"` seen here is *not* in that table, so it falls through to the `else` branch: log a warning and silently default to `"stop"` — **no exception is raised**. Whatever partial/garbage `message.content` came back with it is then treated by ADK as a normal completed turn. The fault itself originates upstream — OpenRouter (or whichever backend it proxied to for that call) surfaced an internal failure as `finish_reason: "error"` instead of a clean HTTP error — but LiteLLM compounds it by making the fault invisible to any caller instead of raising.
**Why F17 doesn't already cover this.** F17's retry-once lives entirely inside `_DebuggerAgentTool.run_async` (`agents.py`), wrapping only calls *to* the Debugger sub-agent — the main per-stage loop (`run_agent`/`_run_agent_once` in `main.py`) has no equivalent protection at all. More importantly, F17 catches Python exceptions (it was built for a raised `JSONDecodeError` on an empty response body); this fault **never raises**, so even copy-pasting F17's `except Exception: retry` pattern onto the main stage loop would not catch it — there is nothing to catch.
**Frequency (checked across all 4 benchmark rounds so far).** `grep -rc "Unmapped finish_reason" benchmarks/alembic/runs/*/logs/*.log` → exactly 2 occurrences, both in the same one `BioSPPy` run, 0 in the baseline/rerun/rerun2/rerun3-biotite/rerun3-AgML logs. Rare (roughly 1 affected run out of ~15 so far), but each occurrence is expensive (~4 min dead time) and, per the near-miss above, is not reliably survivable — a 3rd occurrence in the same stage would have exhausted `MAX_GUARD_RETRIES` and produced `"Agent did not produce a final response."` with no recovery.
**Fix implemented (2026-07-06).** Chasing `map_finish_reason` itself turned out unnecessary and riskier than the alternative: all 9 litellm modules that use it do `from ... import map_finish_reason`, a per-module binding that a single monkeypatch on `core_helpers.map_finish_reason` would not intercept (would need patching all 9, fragile across litellm versions). Instead, hooked litellm's own diagnostic logger — a stable, public integration point: `logging.getLogger("LiteLLM").addHandler(_LiteLLMFaultDetector())` in `main.py`, where `_LiteLLMFaultDetector.emit()` checks `record.getMessage()` for the literal substring `"Unmapped finish_reason 'error'"` and, on a match, sets a `contextvars.ContextVar` (`_transient_provider_fault`) visible to the calling coroutine. (Note: litellm's own redaction filter interpolates `record.args` into `record.msg` and sets `record.args = None` *before* other handlers see the record — an earlier version of this fix checked `record.args` directly and silently never matched; `record.getMessage()` handles both raw and pre-interpolated records correctly.)

`_run_agent_once` (`main.py`) now resets this flag at entry and returns it as a 5th tuple element; `run_agent`'s stage loop wraps each call in an inner `while` loop that retries up to `MAX_TRANSIENT_FAULT_RETRIES=2` times using the *same* message (the agent did nothing wrong) whenever the flag comes back set — entirely separate from `MAX_GUARD_RETRIES`, so a provider hiccup can no longer eat into the budget meant for nudging a genuinely stuck agent.

**Tested (2026-07-06, inside the rebuilt `alembic-base:latest` image):**
- Unit: `_LiteLLMFaultDetector` fires on the exact real warning string, does *not* fire on a different unmapped value or an unrelated warning (2 negative controls).
- Integration: a stubbed `_run_agent_once` that fires the fault on its first call and succeeds on its second confirms `run_agent` retries exactly once with the identical message, then returns the real result — guard-retry counters untouched.
- Exhaustion safety: a stub that fires the fault on *every* call confirms the total call count is bounded (`(MAX_TRANSIENT_FAULT_RETRIES+1) × (MAX_GUARD_RETRIES+1) = 12`, no infinite loop) and falls through to the existing guard-nudge/give-up path.
- A live targeted rerun on `AgML`/`BioSPPy` (the two repos where F22/F23 were found) is the final end-to-end check — see `benchmarks/alembic/runs/2026-07-06_rerun4_f22-f23-verify/`.
**Effort.** Medium (shared-plumbing change) — implemented and unit/integration-tested; not dependent on the rare fault re-occurring live to trust the mechanism.

**2026-07-06 live rerun result: fault did not recur (expected, given ~1/15 frequency), no regression.** `grep -c "Unmapped finish_reason" logs/*.log` → 0 in both `AgML.log` and `BioSPPy.log`. The retry mechanism remains unit/integration-verified since the live fault didn't fire; that evidence, not this run, is what the fix's correctness rests on.

### F23 — F16's per-debugger-call timeout can be defeated by a chain of individually-bounded subprocess calls
**Problem.** Found in the rerun3 targeted-verification run (`AgML.log`, 2026-07-06), while investigating why `AgML`'s Validator stage produced *no* report at all this run (vs. rerun2, where the same repo's Validator finished cleanly with real 0/2/3 tool verdicts — see the F14 section for context on why per-tool detail matters here). Exact timeline:
- `09:34:47` — validator sends a 6th debugger call, asking it to re-investigate a `ModuleNotFoundError: No module named 'ensemble_boxes'` (a real, ordinary environment-fixing task — install a missing pip package and re-verify).
- **Nothing is logged for the next ~20 minutes** — not even `_DebuggerAgentTool`'s own `"[debugger] call timed out after 600s"` message (`agents.py`), which should have fired at `09:44:47` per `DEBUGGER_CALL_TIMEOUT=600`.
- `09:54:36` — the *outer* Validator `STAGE_TIMEOUT` (1800s, `main.py`) finally fires — itself ~2 minutes late (stage started `09:21:14`; 1800s later is `09:51:14`, not `09:54:36`).
**Root cause (inferred from the evidence, not yet confirmed by reading ADK's scheduler internals).** Every individual subprocess call in `tools/shell.py`/`tools/venv.py`/`tools/invoke.py` already has its own bound (`bash`=15s, `bash_env`=300s "for slow installs", venv setup=240s, tool invocation=900s) — so no single call can hang forever. But `asyncio.wait_for(timeout=600)` (F16's mechanism, wrapping the *entire* debugger sub-agent turn in `_DebuggerAgentTool.run_async`) can only actually cancel at a point where the wrapped coroutine yields control back to the event loop. If the debugger sub-agent's one "turn" internally chains several of those individually-bounded calls together (e.g. a few sequential `bash_env` install attempts while chasing the `ensemble-boxes` fix, each capped at 300s but cumulatively unbounded) before its own reasoning loop naturally yields, the 600s ceiling is real in theory but can't take effect until that chain finishes — which is consistent with both symptoms above: the missing 600s log line, and the outer 1800s timeout itself firing a couple minutes late (it was queued behind the same non-yielding block).
**Why this matters.** F16 was written and confirmed (2026-07-06, first rerun) specifically to stop one stuck debugger call from burning the *entire* Validator budget (the original `biopython` case). This finding shows that guarantee has a real, evidenced gap under at least one condition (a multi-step install-and-verify sub-task), even though F16's fix is otherwise working correctly (it did fire in `BioSPPy`/`auto-sklearn`/`ase` during rerun2, per that section).
**Mechanism confirmed (2026-07-06), not just inferred.** Read ADK's source directly inside the built image: `google/adk/tools/function_tool.py`'s `_invoke_callable()` (lines 223-238) branches on `inspect.iscoroutinefunction(target)` — for a synchronous tool function it does `return target(**args_to_call)`, a **direct, blocking call with no `asyncio.to_thread`/`run_in_executor`**. Since every one of our tool functions (`bash`, `bash_env`, `setup_venv`, `check_venv_compat`, `validate_syntax`, `run_tests`, `invoke_mcp_tool`, `clone_repo`) was a plain `def` using blocking `subprocess.run()`, any one of them fully freezes the asyncio event loop for its entire duration — during which **no** `asyncio.wait_for`-based timeout (neither F16's 600s per-debugger-call timeout nor the outer 1800s stage timeout) can fire, since asyncio's timer callbacks only run when the loop gets control back. A debugger turn chaining a few of these (e.g. several install attempts) can defeat both timeouts simultaneously, exactly matching the observed symptoms.

**Fix implemented (2026-07-06).** Converted all 8 tool functions above to `async def`, each delegating its (renamed) synchronous body to a worker thread via `await asyncio.to_thread(_xxx_sync, ...)` (`tools/shell.py`, `tools/venv.py`, `tools/invoke.py`, `tools/fs.py`). ADK's `_invoke_callable` already branches correctly on `iscoroutinefunction` — no adapter needed on our side beyond the function definitions themselves. Confirmed no other code in the repo calls these functions directly outside of ADK's tool registration (only docstring usage examples), so the sync→async conversion is safe.

**Tested (2026-07-06, inside the rebuilt image):**
- `inspect.iscoroutinefunction()` is `True` for all 8 converted tools.
- Behavioral regression: `bash("echo ...")` and `bash("glob ...")` still return identical output shapes.
- **Core mechanism, positive:** a background "heartbeat" coroutine ticks 14 times (every 0.2s) during a 3s `bash_env("sleep 3")` call — proving the event loop stayed responsive throughout, instead of freezing for the full 3s.
- **Core mechanism, decisive:** `asyncio.wait_for(bash_env("sleep 10"), timeout=1.5)` now correctly raises `TimeoutError` at ~1.5s (previously the timeout was consumed but the coroutine kept running past it, undetected).
- **Negative control (proves the test is real, not a false positive):** the exact *old* pattern — a plain synchronous `subprocess.run()` awaited with no thread offload — was tested against the identical `wait_for(timeout=1.5)` wrapping a `sleep 3`, and it did **not** time out at all (returned normally after the full 3s), confirming this is genuinely what F23 diagnosed and genuinely what the fix resolves.
- A live targeted rerun on `AgML`/`BioSPPy` is the final end-to-end check — see `benchmarks/alembic/runs/2026-07-06_rerun4_f22-f23-verify/`.
**Effort.** Medium-High (touched 4 tool files, ~8 functions, shared across all 5 agents) — implemented and verified via direct source confirmation plus a decisive positive/negative test pair, not just inference.

**2026-07-06 live rerun result: confirmed fixed, with a clean natural reproduction.** `AgML`'s Explorer stage itself genuinely timed out at 900s this run (an unrelated, ordinary slow-repo case — not F19/F20/F21/F22), giving a live F20 cross-check for free: the log correctly shows `STAGE TIMEOUT` with **no** following `[Explorer done]` line, while Environment/Coder/Validator — which really did complete — each got their real `[... done]` line and the pipeline ended with a true `Pipeline complete`. Separately, `BioSPPy` hit a genuine slow debugger call (a `pip install` chain, i.e. exactly F23's scenario) — sent at `10:53:39`, and `[debugger] call timed out after 600s` fired at `11:03:39`, **exactly 600.0s later, to the second**. In the pre-fix rerun3 case, this exact log line never appeared even ~20 minutes after it should have. ### F24 — Validator/debugger handoff has no path for "the sample is wrong," not "the code is wrong," and fixes don't propagate across sibling tools

3. This is squarely adjacent to F1/F4 (deterministic gates) and F3 (held-out validation) already in the optional backlog — a fuller, code-enforced version would likely be designed together with those; the instruction-level version below is the cheap, immediate slice.

### F25 — SKIP is a soft LLM convention, not an enforced gate — and there's no tier for genuinely heavy tools

**Problem.** Found while diagnosing the 2026-07-06 final-eval `AgML` validator timeout (see DEMO_READINESS_TODO.md §1a). The Coder correctly identified `train_detector` as too expensive to sample-invoke and wrote `SKIP` for it in `server.md`'s samples block. `instructions/validator.py` Step 4 says *"For every entry... that is NOT marked SKIP: invoke..."* and *"Tools whose sample is SKIP are reported as skipped — not failures."* The validator invoked it anyway, with the tool's own default `epochs=100` (a real Ultralytics YOLO training run), which then consumed most of the 1800s stage budget before hitting an unrelated dataset-export bug. SKIP is parsed and acted on entirely by the validator LLM reading free-text YAML — there is no code-level check anywhere that actually prevents an `invoke_mcp_tool(train_detector, ...)` call from being attempted.

There's a second, related gap: even when SKIP *is* honored, a genuinely heavy tool (real training, real large-dataset processing) then gets **zero** verification, not even a slow one — the two options today are "cheap enough to fit in the shared 1800s budget" or "never checked at all."

**Spec.**
1. **Make SKIP a hard, code-enforced gate, not an LLM-followed convention.** Parse `reports/server.md`'s `samples:` YAML block programmatically (a small, already-structured block) right before the Validator stage starts, and inject the computed SKIP/invoke split explicitly into the validator's opening message as a concrete list ("Do NOT invoke: train_detector. Invoke only: load_dataset, run_inference, evaluate_detection_model, visualize_dataset_samples.") — a system-computed constraint the LLM is directly told is far more reliable than expecting it to correctly self-filter from a markdown block on every run. Belt-and-suspenders option: have `invoke_mcp_tool` itself refuse a call against a tool name found in the parsed SKIP set, returning `{"skipped": true, "reason": "..."}` instead of running it, so enforcement doesn't depend on the LLM at all.
2. **Add an optional, separate "extended validation" pass for SKIP-marked tools, decoupled from the main Validator's shared timeout.** Not a bigger `STAGE_TIMEOUT["validator"]` for everyone (that punishes every repo's normal-weight tools to accommodate the rare heavy one) — instead, a distinct stage/pass that runs *only* against the tools the main pass skipped, with its own, much larger per-tool budget (tens of minutes), run separately (e.g. via the existing `--resume` mechanism, or a dedicated CLI flag / opt-in benchmark pass) so it doesn't inflate the default per-repo wall-clock cost. Failing this pass still doesn't count as harshly as a main-pass failure — it's closer to "verified as far as time allowed."
3. Cheap immediate mitigation, independent of 1–2: for training/inference-style tools specifically, `coder.py`'s sample-invocation rules should require a genuinely cheap parameterization (tiny epoch count, tiny dataset subset) *in addition to* the option to mark SKIP, mirroring what baseline's `AgML` run did successfully (`epochs=2` — validated for real, cheaply, no SKIP needed) — giving the validator a low-cost path to real coverage instead of an all-or-nothing choice between "full-cost real run" and "no run at all."

**Integration.** (1) is a `main.py`/`agents.py` change (parse `server.md`, thread the computed list into the validator's initial prompt and/or `invoke_mcp_tool`'s dispatch). (2) is a new optional stage, analogous to today's 4-stage pipeline. (3) is a `coder.py` instruction addition next to the existing SKIP rules (`instructions/coder.py` lines ~352–385).
**Effort.** (1) Low–Med. (2) Med (new stage/pass, needs a design decision on where it plugs into `run_benchmark.py`). (3) Low.

**Implemented 2026-07-07 (items 1 and 3; item 2 still deferred — same "post-2026-07-10 backlog" reasoning as F1/F3/F4).**
- **Item 1.** `tools/fs.py`'s new `parse_samples_block(repo_url)` parses `server.md`'s fenced ```` ```yaml ```` `samples:` block via PyYAML (added to `docker/alembic/requirements.txt`) right before the Validator stage starts. `main.py`'s new `_build_validator_message()` computes the SKIP/invoke split and hands the validator an explicit, authoritative list in its opening message instead of relying on it to re-derive the same split from free-text YAML every run. ### F37 — A long in-flight `invoke_mcp_tool` call could keep a container alive well past the stage that spawned it, for zero benefit

**Problem.** Found during the F25 verification run: the Validator's 1800s timeout fired while a debugger-initiated `invoke_mcp_tool(train_yolo_model, ...)` call was mid-flight, actually training a real (if `epochs=2`-capped) YOLO model. `asyncio.wait_for`'s cancellation at the stage boundary can only cancel the *coroutine* awaiting `asyncio.to_thread` — it cannot reach into the worker thread blocked inside `subprocess.run()`, so that thread kept running. The old `subprocess.run(..., timeout=900)` in `_invoke_mcp_tool_sync` would eventually fire and kill its *immediate* child (`invoke_tool.py`) — but that only orphaned the *real* generated-code subprocess it spawned as its own child (`server.py`'s tool function does its own uncapped `subprocess.run()`), which kept running with no cap of its own at all. Net effect: the container (and therefore `start_chain.py`'s foreground `docker run`, and therefore the whole benchmark driver) could not fully exit/commit until roughly `STAGE_TIMEOUT` + 900s had both elapsed, for a tool whose result nobody was even going to read (the stage had already given up). Not an unbounded hang (Docker tears down a container's whole process tree once the container itself stops, so nothing leaked past the run), but a real, silent ~15-minute waste with no signal gained — directly prompted by the maintainer's observation that resource-heavy tool calls "waste a lot of time and don't give any benefits."

**Spec/fix.** Two changes, both in `tools/invoke.py`'s `_invoke_mcp_tool_sync`:
1. Shrink the timeout from 900s to `_INVOKE_TIMEOUT = 120`s. `coder.py` already requires every non-SKIP sample to be "cheap to run" — a genuinely cheap call should return in seconds, so anything still running past 120s is resource-heavy regardless of how small its parameters look (a real `epochs: 2` run still triggers a genuine dataset download + training loop, as observed).
2. Switch from `subprocess.run` to `subprocess.Popen(..., start_new_session=True)` + `proc.communicate(timeout=...)`, so a timeout can `os.killpg()` the *entire* process group — killing the real generated-code grandchild subprocess too, not just `invoke_tool.py`.
3. A timeout now returns `{"skipped": true, "reason": "..."}` (same shape as F25's SKIP-gate response) instead of `{"ok": false, "error": "timed out"}` — so it's reported as SKIPPED, not FAILED, and never triggers a wasted debugger call. The `reason` text makes clear this is not a confirmed bug, just a call too slow for a fast validation pass, and points at F25 item 2 (the still-deferred decoupled "extended validation" pass) as the real fix for tools that need more room. `validator.py` and `debugger.py` both updated to explain the dual meaning of `{"skipped": true}` (explicitly SKIP-marked, or simply timed out) and to treat both identically.

**Effort.** Low.
**Implemented and verified 2026-07-07.** Unit-verified standalone (a fake tool spawning a real 600s-sleep grandchild subprocess): the timeout fires at 120.1s, returns the expected `{"skipped": true, ...}` shape, and the grandchild process is confirmed fully killed (`pgrep` found nothing afterward) — not just orphaned. A normal fast call and the existing SKIP-gate case were both re-confirmed unaffected. Rebuilt image, confirmed baked in (`grep -c "_INVOKE_TIMEOUT = 120"` / `grep -c killpg` → 1 each). Not yet re-verified against a real repo end-to-end (would need another resource-heavy tool to naturally arise in a live run) — the standalone reproduction covers the exact mechanism (timeout → process-group kill → SKIPPED classification) that F37 changes.

### F39 — F28's helper-import safety check assumes only two script shapes; a Coder-generated third shape defeats it

**Problem.** Found investigating the same CONCH run's Syntax stage: the first

candidate_texts = json.loads(sys.argv[3])`), with no `argparse.ArgumentParser()`
call anywhere and no `if __name__ == "__main__":` guard. `tools/invoke.py`'s

inverting the old "assume safe unless proven otherwise" default to "assume
unsafe unless a recognized safe pattern is found."

### F28 — `validate_syntax` never checks the helper scripts that contain the actual per-tool logic — extends/concretizes F1

**Problem.** Root-caused while explaining why `aizynthfinder`'s final-eval `expand_molecule` failure (`ImportError: cannot import name 'AiZynthExpander' from 'aizynthfinder'` — a hallucinated class that doesn't exist in the library) wasn't caught by the "Syntax & Imports: PASSED" check before ever reaching a live `invoke_mcp_tool` call. Read `tools/invoke.py`'s `_validate_syntax_sync()`: it `py_compile`s and import-execs **only `server.py`**. The helper scripts under `helpers/*.py` — which contain the actual imports and per-tool logic, and are only ever invoked lazily via `subprocess.run` when a tool is actually called — are never syntax-checked, never import-checked, never touched by this function at all. A hallucinated import/class/function name inside a helper script is therefore invisible until the Validator burns a live invocation attempt (subprocess spin-up, traceback capture) and a full debugger round-trip on something a sub-second static check could have caught for free, in parallel with `server.py`'s own check, before Stage 4 even starts.
**Spec.** Extend `_validate_syntax_sync()` to iterate every file under `helpers/`, and for each: (a) `py_compile` it (catches plain syntax errors), and (b) AST-parse its `Import`/`ImportFrom` nodes and, for each imported name, verify it actually exists on the target module via `importlib.import_module(...)` + `hasattr(...)` inside the server venv — without executing the script's own `main()`/`if __name__ == "__main__":` body (helper scripts are meant to run standalone with argv, so a full `exec_module` isn't safe/meaningful here the way it is for `server.py`). This directly targets the exact failure class found this session (`cannot import name X from Y`) without needing full semantic execution. `coder.py`'s Step 2 ("verify API signatures before writing helpers") should also be extended to explicitly say: grep/read to confirm a class or function **exists** in the target module before importing it, not just that its *parameter names* match — the existing instruction only covers the latter.
**Integration.** `tools/invoke.py`'s `_validate_syntax_sync()` (code). `instructions/coder.py` Step 2, ~line 280–288 (instruction). This is a concrete, low-effort, high-confidence-evidence slice of the long-deferred **F1** (static import/symbol AST gate) — not the full F1 (which also covers `server.py`-level checks and possibly gating tool *selection*, not just post-hoc verification), but the specific gap this session's evidence points at.
**Effort.** Low.

**Implemented 2026-07-06.** `_validate_syntax_sync()` now loops over every `helpers/*.py` file after `server.py`'s own checks pass: `py_compile`s each one (`stage: "helper_syntax"` on failure), then runs `_check_helper_imports()` (`stage: "helper_imports"` on failure). Actual mechanism differs from the original AST+`importlib.hasattr` spec above — it turned out simpler and more robust to **execute the file's own import-safe prefix directly** (via a new `_import_safe_prefix()`, computed by AST-walking top-level statements: `Import`/`ImportFrom`/`FunctionDef`/`ClassDef` nodes are always safe to include since defining doesn't execute; any `if __name__ == "__main__":` guard is skipped entirely; a top-level statement whose source segment contains `ArgumentParser(`/`parse_args(` is the real business-logic boundary and stops the walk there) than to reimplement `importlib`-based symbol resolution by hand — this reuses Python's own real import machinery instead of re-deriving it, and naturally also catches plain `SyntaxError`s inside the prefix.

Two real bugs surfaced and were fixed during testing, both instructive about how easy this class of check is to get subtly wrong:
1. **`sys.path[0]` semantics differ between `python -c "..."` and running a real script file.** The first version ran the prefix via `-c`, which sets `sys.path[0]` to `''`/cwd; server.py always invokes helpers as a real file (`subprocess.run([python, helper_path, ...])`), which sets `sys.path[0]` to the *script's own directory*. This produced a spurious failure on an `aizynthfinder` helper that genuinely imports fine at real invocation time. Fixed by writing the prefix to a temp file *in the same directory as the original helper* and invoking that file directly, matching real semantics exactly.
2. **Two-venv repos need the repo venv, not the server venv, to check helper imports.** Helper scripts import the repo's own packages; in two-venv mode (`coder.py`'s `PYTHON = _REPO_VENV if _REPO_VENV.exists() else _SERVER_VENV`) those live in `.venv-repo`, while `.venv` only has `fastmcp`/`pytest`/`mcp`. Checking against `paths.py`'s existing `venv_python()` (hardcoded to `.venv`) produced false `ModuleNotFoundError`s for `numpy` (on `ase`) and `joblib` (on `auto-sklearn`) — both real two-venv repos where the package genuinely is installed, just repo-side. Fixed by adding `helper_venv_python()` to `tools/paths.py`, mirroring server.py's own venv-selection logic exactly, and using it for the helper-script checks specifically (server.py's own check correctly keeps using the server venv, since server.py itself never imports repo packages directly).
3. A third edge case, found (not a bug, handled correctly by design): helper scripts come in two observed shapes — flat top-level code with no function wrapper (the documented `coder.py` template) and a `def main():`-wrapped style some runs produce instead (confirmed in `astronomy`'s helpers) where `ArgumentParser(` appears *inside* the function body, not at module top level. A naive text-line cutoff mid-truncates the function definition in the second case (`IndentationError: expected an indented block`) — this is exactly why `_import_safe_prefix` walks AST *statements*, not source lines: a `FunctionDef` node is included whole (regardless of what's textually inside its body) since defining a function never executes it.

**Testing.** A synthetic, fully-controlled 3-file test (a real working cross-module import, a hallucinated-symbol import, and a plain `SyntaxError`) confirms the exact intended behavior with no ambiguity about ground truth. Cross-checked against all 11 real committed images from the 2026-07-06 final-eval run (`docker run` with the new code bind-mounted over the stale baked-in copy): **zero false positives** once both bugs above were fixed, and it caught two real, previously-invisible bugs: `aizynthfinder`'s still-broken `expand_molecule.py` import chain, and — the more striking case — `biotite`'s `run_blast.py` containing `def query_seq = ProteinSequence(...)` (a flatly invalid `def`-as-assignment typo). The latter tool was marked `SKIPPED` by the Coder's own sample block in the real run, meaning the validator never invoked it at all — this genuinely broken, 100%-non-functional tool would have shipped silently undetected without this check; the new static check catches it in milliseconds regardless of SKIP status, since it runs unconditionally on every helper file.

**Live end-to-end confirmation (2026-07-06, `benchmarks/alembic/runs/2026-07-06_rerun7_f26-f28-verify/`, fresh `biotite` regeneration — not a bind-mount replay).** Ran the full pipeline for real with F26/F27/F28 all in place. Coder produced 5 tools (`fetch_and_align_sequences` 5 params, the other four 2-3 params each) — no GUI/notebook-launching tool, no mega-tool; F26/F27's guardrails visibly held. `validate_syntax`'s new checks fired for real on freshly-generated (not synthetic) code and caught 4 genuine bugs before any `invoke_mcp_tool` round-trip was spent on them: a literal `elsif`/`elif` typo (`helper_syntax`) in `perform_msa.py`, and three hallucinated import paths (`helper_imports`) — `biotite.structure.measurements.rmsd`, `biotite.database.pdb.{fetch,PDBFile}`, and `biotite.application.msa.ClustalOmegaApp` (confirmed against the real repo source: `ClustalOmegaApp` actually lives in `biotite.application.clustalo`, not a `.msa` submodule — this one was a genuine F1-class hallucination, not a false positive). The debugger fixed the first two on the first attempt; the third (`ClustalOmegaApp`) repeated with the identical error across 3 attempts, and the validator correctly gave up on that stage per its own "stop on repeated error" instruction rather than looping — exactly the intended behavior. Zero false positives observed.

### F29 — The debugger's internal steps are invisible in the pipeline log — everything but its final self-report is a black box

**Problem.** `agents.py`'s `debugger_agent` runs as an ADK `AgentTool` (via `_DebuggerAgentTool`) nested inside the validator's own agent turn. `AgentTool.run_async()` (ADK library code) spins up its own internal `Runner` and iterates that sub-run's event stream itself, extracting only the final merged text to return to the validator — none of those inner events (the debugger's own `bash`/`read_output_file`/`update_file`/`bash_env`/`invoke_mcp_tool` calls, or its intermediate reasoning) ever pass through `agent_runtime._log_event`, which only sees events from the *top-level* `runner.run_async()` loop each stage (`_run_agent_once`) drives directly. The result: every debugger call appears in the log as exactly two lines — `[validator] CALL debugger({...})` and, minutes later, `[validator] RESP debugger → {'result': '<one-paragraph summary>'}` — with the entire multi-step investigation in between completely opaque. When a debugger call ran ~10 minutes (see F28's live-run writeup above) or hit the 600s `DEBUGGER_CALL_TIMEOUT`, there was no way to tell after the fact whether it made real progress, looped, or got stuck on something unrelated to the reported error.
**Spec.** Attach ADK's `before_tool_callback` / `after_tool_callback` / `after_model_callback` to `debugger_agent` itself — these fire on every tool/model turn the agent takes regardless of whether it's run top-level or nested inside an `AgentTool`, which is the key property that makes this work without reimplementing any of ADK's internal `Runner`/session-management code. Tag each logged line with which top-level validator→debugger call it belongs to, since the validator can invoke the debugger many times per stage and the callbacks alone have no way to distinguish calls.
**Integration.** `agents.py` only. No change to `agent_runtime.py`, `main.py`, or any instruction file.
**Effort.** Low.

**Implemented 2026-07-06.** Added `_debug_round` (a `contextvars.ContextVar[int]`) plus three module-level callback functions — `_debugger_before_tool`, `_debugger_after_tool`, `_debugger_after_model` — mirroring `agent_runtime._log_event`'s existing CALL/RESP/text format (reusing its `_trunc` helper for consistent truncation), attached to `debugger_agent` via the `before_tool_callback`/`after_tool_callback`/`after_model_callback` constructor kwargs. `_DebuggerAgentTool.__init__` now tracks a per-process `self._round` counter, incremented and stamped into `_debug_round` at the start of every `run_async` call (wrapped in a `try`/`finally` so a `── round N start ──` / `── round N end ──` banner brackets the call even on the timeout/exception paths). Every debugger-internal log line now reads `[debugger#N] CALL <tool>(...)` / `[debugger#N] RESP <tool> → ...` / `[debugger#N] text: ...`, directly comparable in format to how `[validator]`/`[coder]`/etc. lines already read for the top-level agents.

**Testing.** Verified the exact ADK callback invocation contracts against the installed library source (`google/adk/flows/llm_flows/functions.py` for before/after-tool: called as `callback(tool=..., args=..., tool_context=...)` and `callback(tool=..., args=..., tool_context=..., tool_response=...)`; `base_llm_flow.py` for after-model: `callback(callback_context=..., llm_response=...)`) to confirm the new functions' parameter names match by keyword and that returning `None` from each (as they do) correctly means "don't override," not "suppress." ### F30 — Successful `invoke_mcp_tool` results had no size cap, unlike stdout/stderr — a plausible (not confirmed) trigger for a provider-side crash

**Problem.** Found while investigating why the `BioSPPy` F24-verification run (`benchmarks/alembic/runs/2026-07-06_rerun8_f24-verify/`) ended without ever writing `validation.md`: right after the debugger fixed `process_ecg` (path resolution, a scipy version incompatibility, and a `ReturnTuple`-vs-`dict` bug — three real, unrelated fixes, all correctly diagnosed and verified), the validator's own top-level LLM calls started failing with `[validator] ERROR in event loop:` — a raw, uncaught litellm `Exception()` surfacing from `convert_to_model_response_object`, a different signature from F22's known "unmapped finish_reason" case. This exact crash recurred identically on the main attempt AND all 3 subsequent guard retries, burning the entire guard-retry budget (`guard_exhausted`) before the validator ever reached `process_ppg`/`process_acc`/`process_resp`/`process_eda` or called `write_report`.

**Important caveat on causation, added after direct scrutiny of the traceback:** the exception bottoms out at `convert_dict_to_response.py:525: raise raised_exception`, where `raised_exception` was a **bare `Exception()` with no message at all** — litellm's own mapper then wraps that into the generic `BadRequestError: OpenrouterException - Provider returned error` label. There is no status code, response body, or "context length"/"token" wording anywhere in the traceback — unlike the separately-observed `biotite` run crash, which showed an explicit, readable `"input (620756 tokens) is longer than the model's context length (262144 tokens)"` message from the provider. So this specific crash is **not confirmed** to be a context/payload-size issue — it's a plausible hypothesis based on timing correlation (the crash started immediately after a very large, unbounded tool result entered the conversation) plus a structurally sound mechanism (see below), not a proven root cause. It's equally consistent with unrelated OpenRouter backend flakiness that litellm also failed to report cleanly.

The plausible mechanism regardless: `process_ecg`'s successful result is a `dict` of full-length numpy arrays (`ts`, `filtered`, `rpeaks`, `templates_ts`, `templates`, `heart_rate_ts`, `heart_rate`) — for a real signal file, many thousands of raw floats, serialized to plain JSON lists by `tools/scripts/invoke_tool.py` with **no size limit at all**. Compare `tools/paths.py`'s `MAX_BYTES = 40_000`, which already caps stdout/stderr text (pytest output, syntax-check errors) before it reaches the LLM — a *successful* `invoke_mcp_tool` result had no equivalent cap and was returned verbatim, becoming part of the ADK session's conversation history and replayed as context on every subsequent LLM call for the rest of the stage.
**Spec.** Cap large `result` payloads from a successful `invoke_mcp_tool` call before they re-enter the conversation — recursively truncate list/array fields to a small prefix + count note, and long strings similarly, rather than the full data.
**Integration.** `tools/invoke.py`'s `_invoke_mcp_tool_sync` — the same function that already truncates `stderr` on the failure path (`r.stderr[-2000:]`), extended to also cap the `result` field on the success path. Chosen over a framework-level `after_tool_callback` cap (also considered, would only touch `debugger_agent`, not the validator's own direct `invoke_mcp_tool` calls) because it fixes the payload at its one single source, for every consumer (validator, debugger, and any future caller) at once.
**Effort.** Low.

**Implemented 2026-07-06.** Added `_truncate_large_result()` to `tools/invoke.py`: recursively walks the result value, capping any `list` to its first `_RESULT_MAX_LIST_ITEMS = 20` items (appending a `"... (N more items truncated)"` marker) and any `str` to `_RESULT_MAX_STR_LEN = 2000` chars (with a similar marker), while passing through dicts/scalars/booleans untouched so field names and a representative sample of real values stay visible to the LLM. Applied in `_invoke_mcp_tool_sync` only on the success path (`parsed.get("ok")` True), right next to the existing failure-path `stderr` truncation — the error/traceback/stderr fields on a failure were already bounded and are untouched.

**Testing.** Verified `_truncate_large_result` directly inside the real `alembic-base` container (bind-mounted) against a synthetic nested payload (a 5000-element list, a 100-element nested list, a 5000-char string, booleans, and a short untouched list): confirmed the long list truncates to 21 items (20 + marker) preserving the correct head values, the nested list truncates identically, the string truncates to `2000 + marker` chars, booleans and short lists pass through unmodified, and dict key structure is fully preserved throughout. Docker image rebuilt with the fix baked in. Not yet re-verified in a full live pipeline run (that would also serve as an indirect check on the causation question above — if the same crash recurs on a rerun with this cap in place, that would weigh against the size-based theory; if it doesn't, that's suggestive but still not conclusive given transient-fault base rates).

### F32 — Stage timeouts (Explorer 900s, Validator 1800s) are the dominant failure mode, and they compound: an Explorer timeout starves every downstream stage

**Problem.** Found in the 2026-07-07 full 12-repo rerun (`benchmarks/alembic/runs/2026-07-07_full-rerun/`, all of F24–F31 in place): of the 11 reachable repos, **5 lost all real signal purely to a stage timeout, not an unfixable bug** — `main.py`'s aggregate metrics confirm this precisely: `"validator": "6/10"` (4 of the 10 repos that reached the Validator stage never finished it — `AgML`, `BioSPPy`, `aizynthfinder`, `auto-sklearn`, all hitting the 1800s `STAGE_TIMEOUT`) and `"explorer": "9/11"` (2 repos — `astropy`, `biotite` — never finished Exploration within 900s). This is not new in kind (F16/F20 already address a *single stuck debugger call* burning the whole budget, and confirmed their fix still works correctly here — every timeout in this run logged the honest "Pipeline incomplete" banner, never a false success claim) — what's new is the scale and a previously uncatalogued **cascade** pattern:

- **The aggregate-budget problem, distinct from F16.** F16 bounds one stuck debugger *call* (600s) so a single hang can't eat the stage. But `AgML`/`BioSPPy`/`aizynthfinder`/`auto-sklearn` didn't hang on one call — each ran several genuinely-productive, individually-fast debug rounds (validator re-check → real new failure → new debugger call → fix → re-check finds a *different* real problem → repeat), and simply had more real, distinct problems than fit in 1800s total. F24's independent re-verification (validator re-running `validate_syntax`/`run_tests`/`invoke_mcp_tool` itself after every debugger claim, instead of trusting the self-report) is doing exactly its job here — it caught a false "tool re-invoke OK" claim on `auto-sklearn` round 3 that was still failing — but each such catch costs a full extra validator-driven tool call plus another debugger round, which is correctness bought with wall-clock time the fixed 1800s budget doesn't have room for. This is very likely a factor in why the "repos with any real validator data" denominator dropped from 10 (final-eval) to 6 (this run) even though the tool-level pass rate among that shrunk set held roughly steady (see DEMO_READINESS_TODO.md's updated §1a table) — plausible mechanism, not proven, since no direct pre/post F24 timing comparison exists on the same repo.
- **New: the Explorer-timeout cascade.** `astropy` and `biotite` both hit the Explorer's 900s timeout without ever writing `exploration.md`. The pipeline correctly continues to the next stage regardless (by design), but downstream stages then operate on missing context: `astropy`'s Environment/Coder stages proceeded without real exploration data and the Coder later crashed on a real bug (see F33) while trying to compensate by exploring `astropy/`'s source directly, ending with `"[validator] required artefacts missing... skipping validator stage"` — total loss, no validation.md at all. `biotite`'s Environment stage self-reported `FAILED` ("exploration report missing"), which meant the venv (including `pytest`) was never properly set up; the Validator stage then had to spend part of its **own** 1800s budget just installing `pytest` before it could even attempt real validation — a compounding risk (each upstream timeout eats into the next stage's budget) that happened to still finish under budget for `biotite` (ended PASSED, 3/0/1 tools) but easily could not have.

**Spec.** Two independent mitigations:
1. **Write a partial/best-effort report on stage timeout instead of nothing.** Right now a timed-out stage returns `""` (correctly logged as honest failure per F20) but produces zero artifact. Even a partial `exploration.md`/`validation.md` reflecting whatever was learned before the deadline (an explicit forced "write what you have now" nudge in the final ~15% of the budget, reusing the existing guard-retry mechanism) would preserve *some* signal instead of all-or-nothing.
2. **Detect and log the cascade explicitly.** When Environment/Coder/Validator starts and finds its expected upstream report missing, it already handles this gracefully (no crash) — but nothing currently flags "this failure is a second-order consequence of an earlier stage timeout" in the final summary. Tagging this explicitly (e.g. `abort_reason: "upstream_stage_timeout"` in F12's metrics) would let the benchmark harness and paper narrative distinguish "genuinely hard repo" from "starved by an earlier timeout" instead of conflating both into one FAILED/ERROR row.
**Effort.** Medium for (1). Low for (2), not yet done.
**Implemented 2026-07-07 (mitigation 1 only).** `agent_runtime.py`'s `_run_agent_once` now accepts a `deadline` (a `time.monotonic()` soft cutoff, checked once per streamed event, same place as the `MAX_STEPS` check). `main.py`'s `_run_stage` computes this as `started + STAGE_TIMEOUT[stage] * REPORT_GRACE_FRACTION` (`REPORT_GRACE_FRACTION = 0.85`, i.e. the last 15% of every stage's budget is reserved as a grace window) and passes it into every `run_agent` call. Crossing the soft deadline breaks the agent's current attempt early with `abort_reason="soft_deadline"` instead of continuing until the hard `asyncio.wait_for` timeout cancels everything; `run_agent`'s existing guard-retry loop then fires one urgent, deadline-free nudge ("you are almost out of time, call write_report IMMEDIATELY, a partial/FAILED report is acceptable, do not call any other tool first") — reusing the same nudge mechanism that already forces a `write_report` call after a `tool_repeat`/`tool_cycle`/`max_steps` abort (see the `biotite` cycle-breaker case in DEMO_READINESS_TODO.md), just triggered on wall-clock instead of a loop pattern.
**Known limitation, closed by F35:** the soft-deadline check only runs *between* streamed events, so it cannot preempt a single very long in-flight tool call (e.g. a debugger round approaching its own F16 600s cap) that starts just before the soft deadline — in that specific case the hard `STAGE_TIMEOUT` can still fire first with nothing saved. This mechanism is a strict improvement (never worse than the prior all-or-nothing behavior) but was never meant to be a 100% guarantee on its own; mitigation 2 (explicit cascade tagging) is still undone. **Live-verified 2026-07-07 against `auto-sklearn`** (`benchmarks/alembic/runs/2026-07-07_f34-verify/`) — and this exact limitation manifested for real: a single top-level `debugger(...)` call (round 4, itself invoking `invoke_mcp_tool` with `time_left_for_this_task: 3600` — a real auto-sklearn training run) spanned from before the 1530s soft-deadline mark all the way past the 1800s hard timeout with no intervening event to check against, and `validation.md` was lost — the exact failure mode this mitigation cannot cover by itself. See F35, which adds a genuine, out-of-band guarantee for precisely this gap.

### F33 — `tools/fs.py`'s `read_file`/`read_output_file` crash on directory paths with an unhandled `IsADirectoryError`

**Problem.** Found in the 2026-07-07 full rerun's `astropy.log`: the Coder called `read_file(path='astropy/time')` — `astropy/time` is a real package **directory** in the repo, not a file. `Path.exists()` returns `True` for directories, so `read_file`'s existence check (`tools/fs.py`, was line 69) passed, and the very next line (`full.read_bytes()[:MAX_BYTES]`) raised an unhandled `IsADirectoryError`. This propagated as a raw Python exception through ADK's tool-calling machinery rather than a clean `{"error": ...}` dict, corrupting that turn (logged as `Missing tool results for tool_call_id(s): [...]`) and forcing a guard-retry. The Coder never recovered a working context for what it was building and ultimately wrote only a markdown report describing intended tools, never real `server.py`/`test_server.py` content — the Validator correctly detected the missing artefacts and skipped rather than crashing further, but the net result is total pipeline failure. This directly caused `astropy`'s regression from a clean `PASSED` in every prior run (baseline, rerun2, final-eval) to complete failure here — the first time this repo has ever failed this way, strongly suggesting this exact bug (not flakiness) is the cause: the LLM stochastically chose to `read_file` a directory this run, which was always going to crash given the missing directory check, regardless of any other change this session.
**Spec/fix.** Add an `is_dir()` check alongside the existing `exists()` check in both `read_file` and `read_output_file`, returning a clean error dict instructing the agent to use `search()`/`bash('ls')` instead — exactly the kind of defensive input handling F1/F4's "bounded, AST-verified tool selection" theme already argues for at the tool-selection layer, but this is cheaper and narrower: a one-line guard in the two file-reading tools themselves.
**Effort.** Trivial.
**Implemented 2026-07-07.** Fixed in `tools/fs.py`: both `read_file` and `read_output_file` now check `full.is_dir()` before attempting `read_bytes()` and return `{"error": "'<path>' is a directory, not a file. Use search() or bash('ls') to list its contents."}` instead of crashing. Not yet re-verified live (would require re-running `astropy` or another repo where the Coder/Explorer/Debugger happens to pass a directory path) — the fix is narrow and low-risk enough that live re-verification is optional rather than required before considering this closed.

### F34 — `clone_repo` never fetched git submodules, so vendored dependencies silently clone empty and get misdiagnosed as "package not installed"

**Problem.** Found live in the F32 soft-deadline re-verification run against `auto-sklearn`: three separate debugger rounds were burned re-diagnosing the same `ModuleNotFoundError: No module named 'autosklearn.automl_common.common'`, each time concluding "auto-sklearn isn't installed" and trying `pip install auto-sklearn` / suggesting conda — none of which could ever fix it. Root cause, confirmed directly against the running build container's actual clone: `autosklearn/automl_common` is a real git submodule (the repo's own `.gitmodules` points it at `https://github.com/automl/automl_common`), and `tools/fs.py`'s `_clone_repo_sync` cloned with plain `git clone --depth=1` — no `--recurse-submodules` — so the submodule directory is *always* empty after cloning, for this or any repo with submodules. The resulting import error looks exactly like a missing pip package, which is what steered every debugger round toward the wrong fix. In an earlier (separately discarded) run, a debugger round had even papered over the empty file with a fake 2-line stub (`def Backend(): pass` / `def create(): pass`) directly in the repo clone — which doesn't behave like the real code at all and just pushed the failure downstream into confusing signature-mismatch errors in later rounds.

Traced `--depth=1` back to the very first commit that introduced `clone_repo` (`69f9c3b`, "Added explorer and coder agent") — no comment, no rationale recorded; almost certainly just the standard "don't need full history" default for clone speed/disk, unrelated to submodules (which git never fetches by default regardless of `--depth`, `--recurse-submodules` is an orthogonal flag). This is the first repo in the benchmark set to actually surface the gap, but the bug is general — any repo with submodules would hit it identically.

**Spec/fix.** Add `--recurse-submodules` to the clone command. Paired with `--shallow-submodules` to keep submodules shallow too, consistent with the existing `--depth=1` rationale (no need for full submodule history either) — the two flags combine cleanly with no tradeoff.
**Effort.** Trivial.
**Implemented 2026-07-07.** `tools/fs.py`'s `_clone_repo_sync` now runs `git clone --depth=1 --recurse-submodules --shallow-submodules <url> <dest>`. Live-verified by cloning the real `auto-sklearn` repo standalone: `autosklearn/automl_common/common/utils/backend.py` went from empty (0 lines) to its real 649-line implementation. **Re-verified end-to-end through the full pipeline 2026-07-07** (`benchmarks/alembic/runs/2026-07-07_f34-verify/`, rebuilt image confirmed to have the fix baked in): zero `automl_common` errors anywhere in the run, versus 14 occurrences in the immediately preceding pre-fix run. F34 closed.

### F35 — Guarantee a validation report gets written even when the validator stage ends without one (hard timeout or guard exhaustion)

**Problem.** F32's soft-deadline mechanism has a documented gap (see F32 above): it cannot preempt a single very long in-flight tool call spanning the soft-deadline-to-hard-deadline window. Live-verified this actually happening 2026-07-07 (`benchmarks/alembic/runs/2026-07-07_f34-verify/`): a debugger round's `invoke_mcp_tool` call ran a real auto-sklearn training job (`time_left_for_this_task: 3600`) that spanned from before the soft deadline to past the 1800s hard `STAGE_TIMEOUT`, with no intervening validator-level event for the deadline check to fire on — `validation.md` was never written, total loss. There's also a second, independent gap: if `run_agent` exhausts its guard-retry budget (`abort_reason="guard_exhausted"`) without ever calling `write_report`, it still returns *normally* (not via the timeout branch) with some non-empty placeholder final text — `main.py`'s old completion check (`if validator_response: ...`) would have misreported this as "Pipeline complete" even with zero `validation.md` on disk.

**Spec.** A last-resort, out-of-band guarantee that doesn't depend on any in-loop event boundary at all: after the validator stage ends (regardless of *how* it ended), check whether `validation.md` actually exists on disk. If not, invoke a separate, narrowly-scoped `reporter_agent` to write one. Two deliberate design choices, both to avoid repeating the validator's own failure modes:
1. **Separate agent, not a re-call of the validator.** The validator got stuck because its own toolset (`debugger`, `invoke_mcp_tool`) let it wander into a long-running call. Re-invoking the *same* agent with the *same* tools doesn't fix that. `reporter_agent`'s toolset is deliberately just `read_report`/`validate_syntax`/`run_tests`/`write_report` — no `debugger`, no `invoke_mcp_tool` — so it is structurally unable to repeat the failure, not just instructed not to. `validate_syntax` (30s) and `run_tests` (120s) are both independently bounded, so the reporter's own call is wrapped in a generous-but-real 300s (`REPORTER_TIMEOUT`) outer cap as defense in depth, not an expected-to-fire limit.
2. **Fresh session, not the validator's cancelled one.** Reusing the validator's own session risks replaying a dangling `function_call` with no matching `function_response` if cancellation happened mid-tool-call — the same "Missing tool results for tool_call_id(s)" corruption pattern that caused the `IsADirectoryError` crash earlier this session (F33). Instead, a lightweight `progress` dict (F35's own addition to `agent_runtime.py`) is mutated in place as the validator's events stream — `tool_calls`, `last_debugger_request`, `last_failure` — and survives cancellation because plain dict mutations aren't rolled back when a coroutine is cancelled. The reporter's prompt gets a compact summary built from this dict instead of the raw (possibly corrupted) transcript.

**Effort.** Medium.
**Implemented 2026-07-07.**
- `agent_runtime.py`: `_run_agent_once`/`run_agent` accept an optional `progress: dict | None` parameter, threaded through unchanged across guard-retry attempts; mutated in place with `tool_calls` (live reference to the same dict already tracked), `last_debugger_request` (on every `debugger(...)` call), and `last_failure` (on every failing `validate_syntax`/`run_tests`/`invoke_mcp_tool` response).
- `instructions/reporter.py` (new): a short, narrowly-scoped instruction — read the coder's report, run `validate_syntax`/`run_tests` once each (no retries, no debugger — it doesn't have one), write a report marked `## Result: INCOMPLETE` folding in whatever context summary it was given.
- `agents.py`: new `reporter_agent`, tools `[read_report, validate_syntax, run_tests, write_report]` only.
- `main.py`: new `_ensure_validation_report(progress)` helper, called unconditionally right after the validator's `_run_stage` call returns (covers both the hard-timeout and guard-exhausted paths in one place) — no-ops immediately if `validation.md` already exists. New `f"{name}_reporter"` session created alongside the other four. The pipeline's own completion check (`Pipeline complete` vs `Pipeline incomplete` log banner) now checks `validation.md`'s existence on disk directly instead of trusting the validator's returned text, since that text is meaningless in both the hard-timeout ("") and guard-exhausted (stale placeholder) cases the fallback exists to cover.
**Live-verified 2026-07-07** during the F25 verification run against `AgML` (`benchmarks/alembic/runs/2026-07-07_f25-verify/`): the Validator hit its 1800s `STAGE_TIMEOUT` mid-debug-round, `main.py` logged `"no validation.md after the stage ended — invoking the fallback reporter..."`, and the reporter produced a real, correctly-structured `## Result: INCOMPLETE` report (syntax/tests results plus all 4 tools marked SKIPPED with the fallback's own reason) within ~2 minutes — the pipeline then correctly logged `"Pipeline complete: AgML"` (file exists, even though its content says INCOMPLETE) instead of losing the run's signal entirely. F35 closed.

### F36 — `MAX_TOOL_CYCLE`'s non-consecutive check aborts tools whose own instructions require repeated identical-args calls (`check_venv_compat`, `validate_syntax`, `run_tests`)

**Problem.** Found live during the F25 verification run's first attempt (before the fix, discarded): the Environment stage's `check_venv_compat(repo_url, venv_name=".venv")` call was aborted via `"tool_cycle"` (`agent_runtime.py`'s non-consecutive `call_key_counts` guard, `MAX_TOOL_CYCLE = 3`) even though each round found genuinely different conflicts (first `albumentations`/`torch` missing, then clean, then `torchmetrics.IoU`/`pytorch_lightning.LightningLoggerBase`) — real progress, not a stuck loop. ### F45 — A NameError past F28's execution boundary was invisible until live invocation; added a zero-execution-risk whole-file undefined-name check

**Problem.** Found in the same `MUSK`/`MedSAM`/`PathFinderCRC`/`STAMP` verification run's remaining `STAMP` failure: `generate_heatmaps.py` used `torch.cuda.is_available()` with no `import torch` anywhere in the file — a plain missing import. F28's `_check_helper_imports` deliberately only executes `_import_safe_prefix`'s safe slice (imports + defs + the argparse-gated prefix) to avoid running real business logic — by design, exactly the design F39 hardened. But that means any name referenced only *inside* the unexecuted business-logic tail is structurally invisible to F28, and only surfaces as a `NameError` at real `invoke_mcp_tool` time, burning a debugger round-trip on something purely static analysis could catch for free.

**Spec/fix.** Added `_find_undefined_names(source)` (`tools/invoke.py`) — a whole-file, zero-execution AST pass (no subprocess, no risk of running anything): collect every name bound anywhere in the file (imports, assignments, function/class defs, parameters, for/with/except/comprehension targets, walrus, global/nonlocal) into one flat set, collect every `Name(Load)` reference anywhere in the file, and flag any reference not in the bound set and not a builtin. Deliberately **whole-file permissive, not properly scoped** — a name bound anywhere in the file (even a different function) counts as defined, trading a rarer class of scope-related bug for zero false positives on legitimate code. Bails out (returns no findings) on a wildcard import (`from x import *`), since that can bind anything and defeats static analysis. Runs before `_check_helper_imports` in `_validate_syntax_sync`'s per-helper loop, so it fires on the very first Syntax check, not after a live invocation.
**Effort.** Low.
**Implemented and tested 2026-07-08.** Unit-tested standalone against 5 cases: (1) a synthetic reproduction of STAMP's exact bug (`torch` referenced, never imported) — correctly flagged; (2) a clean file exercising every binding form the checker understands (args, `*args`/`**kwargs`, `with...as`, `except...as`, comprehension targets, tuple-unpacking assignment) — zero false positives; (3) a wildcard import — correctly bails out with no findings; (4) a file with a real `SyntaxError` — correctly defers to the existing `py_compile`/exec checks rather than erroring itself; (5) a name bound in one function and referenced in a sibling function — correctly NOT flagged, confirming the deliberate whole-file-permissive design choice. Also ran against all 21 real `.py` files in `CoScientist/alembic` itself as a stand-in for "well-formed generated code" — zero flags, confirming no false-positive risk on legitimate code before touching any live repo.
