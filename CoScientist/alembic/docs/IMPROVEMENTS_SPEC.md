# Alembic — Improvement Spec

Consolidated, deduplicated spec of features alembic could adopt, drawn from the ToolRosella and ToolMaker comparisons ([TOOLROSELLA_COMPARISON.md](./TOOLROSELLA_COMPARISON.md), [TOOLMAKER_COMPARISON.md](./TOOLMAKER_COMPARISON.md)) and alembic's current design ([DESIGN.md](./DESIGN.md)). Goal: maximize **stability/robustness** and produce the metrics a paper needs, **without giving up** alembic's edge (autonomous multi-tool, served MCP, two-venv, real in-loop invocation).

## Priority summary

|---|---|---|---|---|

| F2 | Semantic output-correctness gate | High | Low–Med | ToolMaker |
| F3 | Held-out validation invocation | High | Med | ToolMaker |
| F4 | Bounded, AST-verified tool selection | Med–High | Med | ToolRosella |
| F5 | First-class conda / `environment.yml` | Med | Med | ToolRosella |
| F6 | External resource acquisition (weights/datasets) | High | Med–High | ToolMaker |
| F7 | Declared, allowlisted repo-secret injection | Med | Low–Med | ToolMaker |
| F8 | Reproducible image from recorded `install.sh` | High | Med | ToolMaker |
| F9 | Fresh-checkpoint isolation per attempt | High | Med | ToolMaker |
| F10 | Persistent failure-memory across debug | Med | Low | ToolMaker |
| F11 | Tiered model routing | Med | Low | ToolMaker |

Suggested first wave (cheap, high-leverage): **F1, F2, F12, F10**. Second wave (the robustness core): **F9, F8, F6, F4, F3**.

**Update (2026-07-06), F25–F28** — found while comparing baseline vs. final-eval runs for `AgML`/`aizynthfinder`/`ase` (see DEMO_READINESS_TODO.md §1a "Final-eval"): SKIP-marker enforcement gap + no tier for heavy tools (F25), tools with no checkable output should never be created (F26), over-parameterized "mega-tools" are a disproportionate failure point (F27), and `validate_syntax` skips the helper scripts where hallucinated imports actually live (F28, a concrete slice of F1). All four are documented in full below; none implemented yet pending a scoping decision.

**Update (2026-07-06), after the 12-repo bench run** (see `benchmarks/alembic/runs/2026-06-30_baseline/summary.md`, logs in `benchmarks/alembic/runs/2026-06-30_baseline/logs/`): five more bugs were caught red-handed rather than inferred from comparison, and they are cheaper and higher-confidence than F1–F13 because we have the exact traceback. **F14–F18 below should run before F1–F13** — several of them are the actual reason today's pass rate looks worse than the pipeline's real capability.

## Validation & correctness

### F1 — Static import/symbol AST gate
**Problem.** The coder can hallucinate function/class names; alembic only catches this at `validate_syntax` (module import) or later via the debugger — expensive.
**Spec.** New deterministic tool `check_symbols(repo_url)` run between coder and validator: AST-scan the cloned repo for public exported symbols per module; AST-parse `server.py` + `helpers/*.py`; flag every `from <mod> import <sym>` (and wrapped call) where `<mod>` is a repo module but `<sym>` isn't exported. Return structured issues; on issues, route back to coder (or debugger Class C) **before** any venv execution.
**Integration.** Add as a tool + a thin gate stage in `main.py` after Coder; reuse `tools/scripts/compat_check.py`-style AST walking.
**Effort.** Low.

### F2 — Semantic output-correctness gate
**Problem.** `invoke_mcp_tool` only reports `{ok: True/False}` (no exception). A tool can run cleanly and return garbage — common for scientific tools.
**Spec.** After a successful `invoke_mcp_tool`, add an LLM judge that checks the **returned value** against the explorer's documented "Returns"/example: is it plausible, and does it have the expected keys/types/shapes? Emit `{successful, reasoning}`. A `False` verdict triggers the debugger just like an exception.
**Integration.** New step in the Validator instruction + a small `assess_output` helper; feed it the sample's expected-output description from the coder's `samples:` block.
**Effort.** Low–Medium.

### F3 — Held-out validation invocation
**Problem.** Alembic validates with the same samples the coder declared, so a tool that hard-codes the demo path/file passes.
**Spec.** Require the explorer/coder to emit, per tool, **two** invocations with *different* real inputs (e.g. a second sample file, different params). Validator must pass **both**; a tool that only passes its own demo args is marked FAILED (overfit).
**Integration.** Extend the coder `samples:` schema to `examples: [primary, holdout]`; Validator Step 4 loops over both.
**Effort.** Medium (depends on repos shipping ≥2 inputs; fall back to param variation).

## Tool selection

### F4 — Bounded, confidence-ranked, AST-verified tool selection
**Problem.** The explorer proposes "1–5 scenarios" via prompt only — uncapped, unverified, signatures guessed.
**Spec.** Deterministic post-processing of explorer output: (a) hard cap on total tools (e.g. ≤12); (b) per-tool confidence tiers with per-tier caps (high→5/med→3/low→1); (c) **intersect** proposed function/class names with the repo's actual AST symbols, dropping `test`/`example`/private; (d) capture each kept symbol's **real parameter names** and pass them into the coder so wrappers use correct argv (pre-empts wrong-kwarg `TypeError`s the debugger currently fixes reactively).
**Integration.** Run between Explorer and Coder; reuse F1's AST symbol scan; thread `function_signatures` into the coder prompt.
**Effort.** Medium.

## Environment & resources

### F5 — First-class conda / `environment.yml` path
**Problem.** Alembic reaches conda only as "Attempt 3"; scientific repos (rdkit, openbabel, pinned CUDA) often need it.
**Spec.** Promote conda + `environment.yml` to a primary environment strategy alongside uv: detect `environment.yml`, honor channels, use `--solver=libmamba`, install conda deps then the pip section. Keep two-venv semantics (conda env = repo venv; server venv stays Py≥3.10 with fastmcp).
**Integration.** Extend `tools/venv.py` (`setup_venv`) + the Environment instruction's decision tree.
**Effort.** Medium.

### F6 — External resource acquisition (weights download, dataset mounts)
**Problem.** Neither alembic nor ToolRosella fetches pretrained weights/models or README-only-mentioned downloads — a dominant failure cause for ML repos.
**Spec.** Add a resource step in the Environment/build phase: (a) the agent may **download model weights** (README-driven, `huggingface-cli`/`wget`/`gdown`, gated by `HF_TOKEN` via F7), recording fetches so they're baked into the image; (b) **datasets/large inputs are NOT baked** — declare them as mount points / sample paths supplied at invocation time. Explorer notes required artifacts in `exploration.md`; Environment acts on "download weights" but defers "needs dataset" to a mount.
**Integration.** New Environment instruction section + allow `bash_env` to run download CLIs; document a `mounts:`/inputs convention for the served container.
**Effort.** Medium–High.

### F7 — Declared, allowlisted repo-secret injection
**Problem.** Alembic injects only its own LLM keys (and scrubs them); a repo-required runtime secret (HF token, inference API key) has no channel, so token-gated tools can't be built or served.
**Spec.** Support a per-repo `env:` declaration (config/task-level) of required secret names; resolve from host env via an **allowlist** substitution (e.g. `${env:HF_TOKEN}`); inject into build + serve containers; keep them out of the committed image (bake-then-remove, combined with alembic's existing secret scrub). Surface available var names to the agents in prompts.
**Integration.** Extend `start_chain.py` env passthrough + add a substitution util; mention available vars in Environment/Coder instructions.
**Effort.** Low–Medium.

## Reproducibility & isolation

### F8 — Reproducible image from a recorded `install.sh`
**Problem.** Alembic `docker commit`s the mutated build container — opaque, large, hard to audit/reproduce.
**Spec.** Record the Environment agent's **successful** setup commands (venv creation, installs, apt-get, downloads) into an ordered `install.sh` / generated Dockerfile; build the served image with a clean `docker build` from that script instead of committing the dirty container. Keeps the image minimal, reviewable, and deterministically rebuildable.
**Integration.** Log env-agent commands (already partly in `pipeline.log`) into a structured script; swap the commit step in `start_chain.py` for a build step.
**Effort.** Medium.

### F9 — Fresh-checkpoint isolation per validate/debug attempt
**Problem.** Validator/debugger mutate one shared workdir; accumulated side-effects can mask or fabricate failures across iterations.
**Spec.** Freeze the post-install state as a checkpoint (image from F8, or a snapshot of `output/`+venv); before **each** validation/debug attempt, reset the runtime to that checkpoint so every attempt runs against the same clean installed environment. Debug exploration is allowed but discarded; only the code edit persists.
**Integration.** Wrap the Validator loop with a `reset_runtime()` step; pairs naturally with F8.
**Effort.** Medium.

## Agent-loop quality

### F10 — Persistent failure-memory across debug iterations
**Problem.** The debugger is largely stateless per call; alembic only guards with "stop on identical error," allowing oscillating fixes.
**Spec.** Maintain a running list of compact `problem_summaries` (diagnosis + attempted fix) and feed it into each subsequent debug/diagnose prompt ("avoid repeating these"). Use it to detect near-duplicate diagnoses, not just byte-identical errors.
**Integration.** Thread a summaries list through the Validator↔Debugger calls in `main.py`/instructions.
**Effort.** Low.

### F11 — Tiered model routing
**Problem.** One `MODEL` drives every agent; planning/first-implementation benefit from stronger reasoning, the repair loop does not.
**Spec.** Allow per-role model selection: a reasoning model for Explorer planning + initial Coder implementation, a cheaper/faster model for Validator/Debugger iterations. Configurable via env (`MODEL_REASONING`, `MODEL`).
**Integration.** `agents.py` already centralizes `MODEL`; add a second constant and assign per agent.
**Effort.** Low.

## Observability & benchmarking

### F12 — Structured run metrics + error taxonomy
**Problem.** Alembic logs human-readable events but emits no structured per-run metrics or failure classification — exactly the data a paper needs.
**Spec.** Per run, emit a JSON record: per-stage durations, step/tool-call counts, LLM call/token/retry stats, guard/timeout firings, and **every failure classified into a taxonomy** (`ModuleNotFound`/`Import`/`Environment`/`Build`/`Syntax`/`Runtime`/`AttributeError`/`FileNotFound`/…). Aggregate across a benchmark into pass-rate-by-stage and error-distribution tables.
**Integration.** Add a metrics sink alongside the loguru file sink in `main.py`; classify in the Validator/Debugger; aggregate in `run_benchmark.py`.
**Effort.** Low.

**Implemented 2026-07-06.**
- **Classification (`agent_runtime.py`).** `classify_error(text)` maps a raw error/traceback string to one of `ModuleNotFound`/`Import`/`FileNotFound`/`AttributeError`/`KeyError`/`IndexError`/`NameError`/`TypeError`/`ValueError`/`Encoding`/`Syntax`/`Timeout`/`Environment`/`Runtime`/`Unknown`/`Other`, by taking whichever taxonomy needle occurs **last** in the text. This matters because generated `server.py` tool functions wrap the real exception (`raise RuntimeError(f"...: {e.stderr}") from e`), so the wrapper's own class name always appears *before* the wrapped traceback's real exception in the string — "last match wins" recovers the actual root cause (e.g. `ModuleNotFoundError`) instead of the generic `RuntimeError` wrapper. Classification runs inside `_run_agent_once`'s existing event loop, on every `function_response` from `invoke_mcp_tool`/`validate_syntax`/`run_tests` where the tool reports `ok`/`passed` is `False` — no new call sites, no LLM involvement, so it can't add latency or fail independently of the tool call it's classifying.
- **Bonus: F16/F17 visibility.** The debugger's `AgentTool` wrapper (`agents.py`'s `_DebuggerAgentTool`) swallows its own timeout (F16) or exhausted-retry (F17) into a plain text result rather than raising, so those events were previously invisible to any metrics. `_run_agent_once` now recognizes the two fixed strings it returns (`"timed out after"`, `"failed twice"`) and counts them as a `DebuggerTimeout` taxonomy entry — giving F16/F17's firing rate a number for the first time.
- **Per-stage metrics (`agent_runtime.py` → `main.py`).** `run_agent()`'s return type grew from `(final, steps, tokens)` to `(final, steps, tokens, stage_metrics)`, where `stage_metrics = {"tool_calls": {name: count}, "failures_by_class": {label: count}, "guard_retries": int, "transient_fault_retries": int, "abort_reason": "tool_repeat"/"max_steps"/"guard_exhausted"/None}` — aggregated across every guard-retry attempt and F22 fault-retry within the stage. `abort_reason` reflects only the *most recent* `_run_agent_once` call (an earlier attempt's abort is cleared once a later retry finishes clean — see bug fix below), or `"guard_exhausted"` if the guard-retry budget ran out while write_report/venv nudges were still outstanding, overriding a merely-`None` last-attempt status. `main.py`'s `_run_stage()` wraps the call with `time.monotonic()` for wall-clock duration (recorded even on a stage timeout, alongside a `"stage_timeout"` abort reason) and folds everything into `pipeline_metrics`, written to `reports/metrics.json` exactly as before (no schema-breaking rename of the existing `actions_per_stage`/`tokens_per_stage`/`total_actions`/`total_tokens` keys — only new keys added: `durations_per_stage`, `tool_calls_per_stage`, `guard_retries_per_stage`, `transient_fault_retries_per_stage`, `abort_reason_per_stage`, `failures_by_class`).
- **Benchmark-level aggregation (`run_benchmark.py`).** New `aggregate_metrics(records)` rolls every repo's `metrics.json` (already pulled in by `extract_validation()`) into: stage completion counted as `completed/attempted` per stage (a repo only counts as "attempted" a stage if it has a recorded duration, and "completed" if it also has an `actions_per_stage` entry — i.e. didn't time out), and a summed cross-repo `failures_by_class` table. Repos with no `metrics.json` at all (crashed before the `finally` block, or skipped by the pre-flight availability check) are excluded from the denominator rather than counted as stage failures. Appended to `summary.md` as a new `## Aggregate metrics (F12)` section; `summary.json`'s top level changed from a bare list to `{"repos": [...], "aggregate": {...}}` (no other script in the repo consumed the old list-shaped `summary.json`, confirmed by grep before making this change).
- **Two bugs caught by the first live verification attempt, both fixed same-day:**
  1. **`extract_validation()` never read `metrics.json` when `validation.md` was missing.** The function returned early (`{"error": "validation.md not readable", ...}`) the moment the primary report was absent — exactly the case (validator timed out, or was skipped because the coder never produced artefacts) where the richest metrics data exists and matters most. Fixed by always attempting to pull `metrics.json`/`error.json` regardless of whether `validation.md` was readable, merging into whichever base dict (`parse_validation()`'s or the error fallback's) applies. Caught by inspecting a real `biotite` run where `aggregate_metrics()` reported `repos_with_metrics: 0` despite a rich, real `metrics.json` sitting right there in the committed image.
  2. **`abort_reason` accumulated instead of reflecting current state.** The original code only updated `abort_reason` when the current attempt's per-call abort was truthy (`if this_abort: abort_reason = this_abort`), so a stage that aborted once (e.g. `tool_repeat`) and then genuinely succeeded on the next guard-retry attempt would still misreport the stale abort from the failed first attempt. Fixed by unconditionally overwriting `abort_reason` on every attempt (so it always reflects the latest), and by explicitly setting `abort_reason = "guard_exhausted"` when the guard-retry budget runs out with nudges still outstanding (distinct from, and more informative than, whatever the last attempt's own per-call status happened to be — often `None`, since the last attempt can complete with a normal final response and simply never call `write_report`).
- **Testing.** Unit-tested `classify_error()` against 10 cases including two real nested-traceback strings taken verbatim from the `astronomy` rerun5 log (`ModuleNotFoundError` correctly recovered from inside a `RuntimeError` wrapper; `AttributeError` likewise) — all 10 passed. Unit-tested `_tool_outcome()` against all three validation-tool response shapes plus a non-dict guard. Unit-tested `aggregate_metrics()` against a synthetic 4-repo set (one fully-completed, one validator-timeout, one crashed-with-no-`validation`, one unreachable-and-skipped) and asserted the exact expected `stage_completion`/`failures_by_class`/retry totals. Unit-tested the fixed `run_agent()` retry loop against 4 scripted `_run_agent_once` sequences (a stale-abort-clears-on-clean-retry case, a guard-exhaustion case where the last attempt's own status was `None`, a clean single-attempt case, and an F22 fault-retry case confirming fault retries don't consume the guard-retry budget) — all asserted correctly. Live end-to-end verification: `benchmarks/alembic/runs/2026-07-06_rerun6_f12-verify/` (the first attempt at this run was invalidated by an unrelated process-hygiene accident: an earlier foreground invocation's 2-minute CLI timeout killed the host-side orchestrator but left its Docker container running detached and orphaned for 39+ minutes, corrupting the shared host-side log file when a second, correct background invocation wrote to the same path; the orphan was stopped/removed and the run redone cleanly).

**2026-07-06 clean live-run confirmation.** Re-ran `biotite` end-to-end: **PASSED**, 4/4 tools, 12/12 tests, exit 0, 1142.5s. `reports/metrics.json` (pulled straight from the committed image) now carries every new F12 key with sane values: `durations_per_stage` for all 4 stages (135.4/40.9/249.5/707.0s), `tool_calls_per_stage` with a full per-tool breakdown per stage (e.g. `validator`: `invoke_mcp_tool: 5, debugger: 5, run_tests: 2, ...`), `guard_retries_per_stage`/`transient_fault_retries_per_stage` all `0` (none needed this run), `abort_reason_per_stage: {}` (correctly empty — no stage aborted, confirming the fixed accumulation logic doesn't fabricate stale aborts when nothing actually went wrong), and `failures_by_class: {TypeError: 3, ModuleNotFound: 1, FileNotFound: 1}` — these are the 5 real `invoke_mcp_tool` failures the validator's debugger cycled through and fixed en route to the final 4/4 PASSED, correctly classified from their raw tracebacks. `summary.json`'s new `{"repos": [...], "aggregate": {...}}` shape resolved to `"repos_with_metrics": 1` (confirming bug #1's fix — `extract_validation()` now reliably surfaces `metrics.json` alongside `validation.md`) with `stage_completion` correctly `"1/1"` for all four stages. No orphaned container left behind afterward (`docker ps -a | grep biotite` empty). The retry-specific paths (an aborted attempt clearing on a later clean retry; `guard_exhausted` firing when the budget runs out with nudges still outstanding) aren't exercised by this particular clean run — that behavior rests on the 4 scripted `run_agent()` unit tests above, plus the original (log-corrupted but metrics.json-valid) `biotite` run that organically hit both a `tool_repeat` abort and full guard-retry exhaustion under the pre-fix code, which is what surfaced bug #2 in the first place. F12 closed.

### F13 — Success-memoized, resumable runner
**Problem.** Alembic wipes the workdir each run; re-benchmarking reprocesses already-solved repos.
**Spec.** Persist a `processed_repos.json` keyed by repo URL + commit; skip repos already converted successfully; combine with the existing `--resume <stage>` for partial reruns. Record per-repo status/artifact path/message.
**Integration.** Wrap `run_benchmark.py` (and optionally `start_chain.py`) with a memo check; reuse the existing resume machinery.
**Effort.** Low.

## Bugs caught in the 2026-06-30 bench run (F14–F18)

### F14 — Validator must not blanket-skip all tools on one test failure
**Problem.** `auto-sklearn` (1 of 17 pytest cases failed on an unrelated kwarg mismatch) and `biotite` (a one-character `SyntaxError` in the generated test file) both ended with **all 4 declared tools marked SKIPPED** — `invoke_mcp_tool` was never called for any of them. The Validator instruction's Step 3 wording ("record the error and proceed to Step 5") is evidently being read as "skip Step 4 entirely" rather than "skip only the affected tool." This directly produced 2 of the 5 FAILED rows in the baseline run's summary and understates the true pass rate — several of those 4×2=8 SKIPped tools likely work fine.
**Spec.** Make per-tool invocation independent of overall `run_tests` pass/fail: only the specific tool(s) implicated by a failing test should be withheld from `invoke_mcp_tool`; every other declared sample must still be invoked and scored PASS/FAIL on its own merits.
**Effort.** Low — tighten the Validator instruction's Step 3→Step 4 transition logic.

### F15 — Debugger request must always carry `repo_url`
**Problem.** In `biotite`, the Validator's one debugger call omitted the repo URL prefix that every other observed call includes; the Debugger replied "cannot locate test_server.py... verify repository URL" and gave up on try 1 of 3 — turning a trivial missing-brace fix into a total stage failure (all 4 tools SKIPPED). The `debugger` `AgentTool` takes a free-text `request: str` with nothing enforcing that `repo_url` is present.
**Spec.** Either make `repo_url` a required structured field on the debugger call (not embedded in free text), or add a pre-flight check that rejects/re-prompts a debugger request missing it.
**Effort.** Low.

### F16 — Per-debugger-call timeout, distinct from the stage timeout
**Problem.** `biopython`'s Validator stage hit its full 30-minute wall-clock timeout while a single debugger call was stuck chasing an `ImportError` (helper scripts `sys.path.insert`-ing into the raw cloned source instead of an installed package, so compiled C-extensions were missing) — the whole budget was consumed with **zero** `validation.md` written, losing all signal for that repo.
**Spec.** Bound each individual debugger round-trip (e.g. 3–5 min) independent of the stage-level timeout, so a stuck call fails fast and the stage can still write a partial report instead of losing everything.
**Effort.** Low — wrap the debugger `AgentTool` invocation with its own timeout in `main.py`.

### F17 — Retry once on transient LLM/API error
**Problem.** In `BioSPPy`, the first debugger call for `process_ecg_signal` never returned: OpenRouter/LiteLLM returned an empty body mid-call → `JSONDecodeError`/`OpenAIError`, caught by `main.py`'s blanket `except Exception: logger.exception(...)`, which silently burned one of the tool's ≤2 debugger attempts with zero diagnostic value.
**Spec.** Classify transient provider errors (empty response, 5xx, rate limit) separately from real failures and retry once (with backoff) before charging it against the attempt budget.
**Effort.** Low.

### F18 — Explorer must propose realistic, domain-sized sample inputs
**Problem.** `BioSPPy` failed 4 of 5 tools because the Explorer's example inputs were toy arrays (a 5-element list for an ECG filter requiring `padlen=4503`, a 5 ms segment where `assess_ecg_quality` requires ≥5 s) — the tools are correct, the *samples* violate the domain's basic preconditions. This is a distinct, cheaper problem than F3's held-out-invocation generalization concern: today's single sample isn't even large enough to exercise the tool once.
**Spec.** Explorer instruction should require sample data sized to the domain (signal duration/length, image dimensions, sequence length) inferred from the repo's own docs/tests/example data, not an arbitrary placeholder shape.
**Effort.** Low — instruction change plus, where the repo ships its own example/test fixtures, prefer sampling from those over synthesizing new toy data.

**2026-07-06 rerun finding — first attempt at F18 (Explorer-only) did not work.** Re-running `BioSPPy` after patching only `instructions/explorer.py` still produced `ecg_processing(signal=[0.1, 0.2, 0.3])` and other 3-5-element arrays, failing with the exact same "signal too short" class of error. Root cause: the concrete `samples:` block that `invoke_mcp_tool` actually runs is written by the **Coder**, not the Explorer, and `instructions/coder.py` had its own, directly conflicting instruction: *"Use the most minimal args you can."* The Coder was never reading the Explorer's sizing guidance for this — it was independently told to minimize. Fixed by rewording `coder.py`'s sample-writing rules to distinguish "cheap to run" (small batch size, CPU device) from "smaller than the function's own precondition," and to check the wrapped function's docstring/call-sites for a minimum size before synthesizing a value.

**2026-07-06 second rerun (rerun2, 11 repos, `coder.py` patch in place) — confirmed fixed at scale.** Cross-checked every `invoke_mcp_tool` call across all 11 executed logs: no repo passed a tiny/all-placeholder numeric array to a precondition-sensitive function anymore. `BioSPPy` now passes `signal: 'examples/ecg.txt'` (a real bundled ECG recording); `astropy` passes real repo-bundled `.fits` test fixtures; `auto-sklearn` copies the repo's own real `load_breast_cancer`/`load_diabetes` example datasets; `ase`/`astronomy`/`aizynthfinder`/`backtrader` all use real physical/chemical/financial parameters. F18 is closed.

One adjacent miss surfaced by the same cross-check (not F18 itself — sizing was never the issue here): **`biotite`** invented plausible-but-nonexistent filenames (`example.fasta`, `example.pdb`, `fixed.pdb`/`mobile.pdb`) instead of the real files it had already seen via `read_file`/`ls` (`doc/examples/download/lysozyme_md.pdb`, `dppc_n128.pdb`, `waterbox_md.pdb`), failing 4/5 tools on "file cannot be read." `coder.py` already had a "Do NOT invent paths" rule, so this is an instruction-following miss, not a missing instruction — strengthened the wording with a concrete counter-example and an explicit "verify the exact path via a directory listing or read_file result first" requirement. Not yet re-benchmarked after this wording change — a stronger, deterministic fix (reject file-path-shaped args that don't resolve inside the container before invocation) is F1/F4's territory, tracked there rather than duplicated here.

### F19 — `_UnknownToolStub` missing attributes
**Problem.** Found in the 2026-07-06 rerun (`backtrader.log`): when the LLM hallucinates a tool name, `main.py`'s `_safe_get_tool` patch returns an `_UnknownToolStub` with only `.name` and `.run_async`; something in ADK's flow also reads `.description` on a tool object, producing `AttributeError: '_UnknownToolStub' object has no attribute 'description'`. This burned a debugger attempt (masked by F17's retry-once, which happened to succeed on the next try — without F17 this would have been a silent wasted attempt like the original BioSPPy case).
**First fix (v1, incomplete).** Added a `description` attribute to `_UnknownToolStub.__init__`.
**2026-07-06 rerun2 finding — v1 was incomplete.** Re-running with the `.description` fix in place, the exact same class of error recurred in `AgML.log` and `BioSPPy.log`, this time for a *different* attribute: `AttributeError: '_UnknownToolStub' object has no attribute 'is_long_running'`. In `AgML` the retry hit the identical error and the debugger call was abandoned as an unresolved failure (graceful, but a genuinely lost attempt). In `BioSPPy` the retry never returned at all — it hung until the Validator's 1800s stage timeout fired, truncating validation after only 1 of 5 tools had been checked, and (see F20) the pipeline log then misleadingly claimed the run had completed. Root cause: `_UnknownToolStub` is duck-typed against ADK's real `BaseTool`, whose full public attribute surface is `name`, `description`, `is_long_running`, `custom_metadata` — the v1 fix patched only the one attribute that had been observed failing, not the class the stub is standing in for.

### F22 — Silent provider fault: unmapped `finish_reason: "error"` burns ~4 min per occurrence, uncaught by F17
**Problem.** Found in the rerun3 targeted-verification run (`BioSPPy.log`, 2026-07-06): during the Coder stage, two separate LLM turns ~4 minutes apart each ended with `LiteLLM:WARNING core_helpers.py:107 - Unmapped finish_reason 'error', defaulting to 'stop'`, followed immediately by a stub/non-actionable "final" response (e.g. *"Now I'll implement the MCP server file..."* with no tool call), which then only recovered via `main.py`'s unrelated `write_report`-guard nudge (`MAX_GUARD_RETRIES=3`, i.e. `[guard] Retry 1/3`, `Retry 2/3`). The stage's `server.py` write finally succeeded on the 3rd attempt, one second before the 1500s Coder `STAGE_TIMEOUT` fired — i.e. the fault very nearly cost the whole stage outright, and did cost ~8 of the 25 available minutes plus 2 of 3 guard-retry slots.
**Root cause (confirmed by reading source inside the built image).** `litellm/litellm_core_utils/core_helpers.py`'s `map_finish_reason()` holds an explicit table mapping every provider's finish-reason string to the OpenAI-standard set (`stop`/`length`/`tool_calls`/`content_filter`/`function_call`) — it even has a deliberate `"ERROR": "stop"` entry for a different provider's uppercase variant. The lowercase `"error"` seen here is *not* in that table, so it falls through to the `else` branch: log a warning and silently default to `"stop"` — **no exception is raised**. Whatever partial/garbage `message.content` came back with it is then treated by ADK as a normal completed turn. The fault itself originates upstream — OpenRouter (or whichever backend it proxied to for that call) surfaced an internal failure as `finish_reason: "error"` instead of a clean HTTP error — but LiteLLM compounds it by making the fault invisible to any caller instead of raising.
**Why F17 doesn't already cover this.** F17's retry-once lives entirely inside `_DebuggerAgentTool.run_async` (`agents.py`), wrapping only calls *to* the Debugger sub-agent — the main per-stage loop (`run_agent`/`_run_agent_once` in `main.py`) has no equivalent protection at all. More importantly, F17 catches Python exceptions (it was built for a raised `JSONDecodeError` on an empty response body); this fault **never raises**, so even copy-pasting F17's `except Exception: retry` pattern onto the main stage loop would not catch it — there is nothing to catch.
**Frequency (checked across all 4 benchmark rounds so far).** `grep -rc "Unmapped finish_reason" benchmarks/alembic/runs/*/logs/*.log` → exactly 2 occurrences, both in the same one `BioSPPy` run, 0 in the baseline/rerun/rerun2/rerun3-biotite/rerun3-AgML logs. Rare (roughly 1 affected run out of ~15 so far), but each occurrence is expensive (~4 min dead time) and, per the near-miss above, is not reliably survivable — a 3rd occurrence in the same stage would have exhausted `MAX_GUARD_RETRIES` and produced `"Agent did not produce a final response."` with no recovery.
**Fix implemented (2026-07-06).** Chasing `map_finish_reason` itself turned out unnecessary and riskier than the alternative: all 9 litellm modules that use it do `from ... import map_finish_reason`, a per-module binding that a single monkeypatch on `core_helpers.map_finish_reason` would not intercept (would need patching all 9, fragile across litellm versions). Instead, hooked litellm's own diagnostic logger — a stable, public integration point: `logging.getLogger("LiteLLM").addHandler(_LiteLLMFaultDetector())` in `main.py`, where `_LiteLLMFaultDetector.emit()` checks `record.getMessage()` for the literal substring `"Unmapped finish_reason 'error'"` and, on a match, sets a `contextvars.ContextVar` (`_transient_provider_fault`) visible to the calling coroutine. (Note: litellm's own redaction filter interpolates `record.args` into `record.msg` and sets `record.args = None` *before* other handlers see the record — an earlier version of this fix checked `record.args` directly and silently never matched; `record.getMessage()` handles both raw and pre-interpolated records correctly.)

`_run_agent_once` (`main.py`) now resets this flag at entry and returns it as a 5th tuple element; `run_agent`'s stage loop wraps each call in an inner `while` loop that retries up to `MAX_TRANSIENT_FAULT_RETRIES=2` times using the *same* message (the agent did nothing wrong) whenever the flag comes back set — entirely separate from `MAX_GUARD_RETRIES`, so a provider hiccup can no longer eat into the budget meant for nudging a genuinely stuck agent.

**Tested (2026-07-06, inside the rebuilt `alembic-base:latest` image):**
- Unit: `_LiteLLMFaultDetector` fires on the exact real warning string, does *not* fire on a different unmapped value or an unrelated warning (2 negative controls).
- Integration: a stubbed `_run_agent_once` that fires the fault on its first call and succeeds on its second confirms `run_agent` retries exactly once with the identical message, then returns the real result — guard-retry counters untouched.
- Exhaustion safety: a stub that fires the fault on *every* call confirms the total call count is bounded (`(MAX_TRANSIENT_FAULT_RETRIES+1) × (MAX_GUARD_RETRIES+1) = 12`, no infinite loop) and falls through to the existing guard-nudge/give-up path.
- A live targeted rerun on `AgML`/`BioSPPy` (the two repos where F22/F23 were found) is the final end-to-end check — see `benchmarks/alembic/runs/2026-07-06_rerun4_f22-f23-verify/`.
**Effort.** Medium (shared-plumbing change) — implemented and unit/integration-tested; not dependent on the rare fault re-occurring live to trust the mechanism.

**2026-07-06 live rerun result: fault did not recur (expected, given ~1/15 frequency), no regression.** `grep -c "Unmapped finish_reason" logs/*.log` → 0 in both `AgML.log` and `BioSPPy.log`. Both pipelines completed all 4 stages cleanly this time (vs. rerun3 where both truncated with "validation.md not readable") — real per-tool verdicts were produced (AgML 1/3/0, BioSPPy 0/5/0), and every tool-level failure traces to genuine, unrelated application bugs (missing ML deps that got installed, a real `KeyError: 'bbox'` in generated code, `argparse` boolean-flag handling, sample-sizing in generated helpers) — none attributable to the F22 fix itself. The retry mechanism remains unit/integration-verified since the live fault didn't fire; that evidence, not this run, is what the fix's correctness rests on.

### F23 — F16's per-debugger-call timeout can be defeated by a chain of individually-bounded subprocess calls
**Problem.** Found in the rerun3 targeted-verification run (`AgML.log`, 2026-07-06), while investigating why `AgML`'s Validator stage produced *no* report at all this run (vs. rerun2, where the same repo's Validator finished cleanly with real 0/2/3 tool verdicts — see the F14 section for context on why per-tool detail matters here). Exact timeline:
- `09:34:47` — validator sends a 6th debugger call, asking it to re-investigate a `ModuleNotFoundError: No module named 'ensemble_boxes'` (a real, ordinary environment-fixing task — install a missing pip package and re-verify).
- **Nothing is logged for the next ~20 minutes** — not even `_DebuggerAgentTool`'s own `"[debugger] call timed out after 600s"` message (`agents.py`), which should have fired at `09:44:47` per `DEBUGGER_CALL_TIMEOUT=600`.
- `09:54:36` — the *outer* Validator `STAGE_TIMEOUT` (1800s, `main.py`) finally fires — itself ~2 minutes late (stage started `09:21:14`; 1800s later is `09:51:14`, not `09:54:36`).
**Root cause (inferred from the evidence, not yet confirmed by reading ADK's scheduler internals).** Every individual subprocess call in `tools/shell.py`/`tools/venv.py`/`tools/invoke.py` already has its own bound (`bash`=15s, `bash_env`=300s "for slow installs", venv setup=240s, tool invocation=900s) — so no single call can hang forever. But `asyncio.wait_for(timeout=600)` (F16's mechanism, wrapping the *entire* debugger sub-agent turn in `_DebuggerAgentTool.run_async`) can only actually cancel at a point where the wrapped coroutine yields control back to the event loop. If the debugger sub-agent's one "turn" internally chains several of those individually-bounded calls together (e.g. a few sequential `bash_env` install attempts while chasing the `ensemble-boxes` fix, each capped at 300s but cumulatively unbounded) before its own reasoning loop naturally yields, the 600s ceiling is real in theory but can't take effect until that chain finishes — which is consistent with both symptoms above: the missing 600s log line, and the outer 1800s timeout itself firing a couple minutes late (it was queued behind the same non-yielding block).
**Why this matters.** F16 was written and confirmed (2026-07-06, first rerun) specifically to stop one stuck debugger call from burning the *entire* Validator budget (the original `biopython` case). This finding shows that guarantee has a real, evidenced gap under at least one condition (a multi-step install-and-verify sub-task), even though F16's fix is otherwise working correctly (it did fire in `BioSPPy`/`auto-sklearn`/`ase` during rerun2, per that section).
**Mechanism confirmed (2026-07-06), not just inferred.** Read ADK's source directly inside the built image: `google/adk/tools/function_tool.py`'s `_invoke_callable()` (lines 223-238) branches on `inspect.iscoroutinefunction(target)` — for a synchronous tool function it does `return target(**args_to_call)`, a **direct, blocking call with no `asyncio.to_thread`/`run_in_executor`**. Since every one of our tool functions (`bash`, `bash_env`, `setup_venv`, `check_venv_compat`, `validate_syntax`, `run_tests`, `invoke_mcp_tool`, `clone_repo`) was a plain `def` using blocking `subprocess.run()`, any one of them fully freezes the asyncio event loop for its entire duration — during which **no** `asyncio.wait_for`-based timeout (neither F16's 600s per-debugger-call timeout nor the outer 1800s stage timeout) can fire, since asyncio's timer callbacks only run when the loop gets control back. A debugger turn chaining a few of these (e.g. several install attempts) can defeat both timeouts simultaneously, exactly matching the observed symptoms.

**Fix implemented (2026-07-06).** Converted all 8 tool functions above to `async def`, each delegating its (renamed) synchronous body to a worker thread via `await asyncio.to_thread(_xxx_sync, ...)` (`tools/shell.py`, `tools/venv.py`, `tools/invoke.py`, `tools/fs.py`). ADK's `_invoke_callable` already branches correctly on `iscoroutinefunction` — no adapter needed on our side beyond the function definitions themselves. Confirmed no other code in the repo calls these functions directly outside of ADK's tool registration (only docstring usage examples), so the sync→async conversion is safe.

**Tested (2026-07-06, inside the rebuilt image):**
- `inspect.iscoroutinefunction()` is `True` for all 8 converted tools.
- Behavioral regression: `bash("echo ...")` and `bash("glob ...")` still return identical output shapes.
- **Core mechanism, positive:** a background "heartbeat" coroutine ticks 14 times (every 0.2s) during a 3s `bash_env("sleep 3")` call — proving the event loop stayed responsive throughout, instead of freezing for the full 3s.
- **Core mechanism, decisive:** `asyncio.wait_for(bash_env("sleep 10"), timeout=1.5)` now correctly raises `TimeoutError` at ~1.5s (previously the timeout was consumed but the coroutine kept running past it, undetected).
- **Negative control (proves the test is real, not a false positive):** the exact *old* pattern — a plain synchronous `subprocess.run()` awaited with no thread offload — was tested against the identical `wait_for(timeout=1.5)` wrapping a `sleep 3`, and it did **not** time out at all (returned normally after the full 3s), confirming this is genuinely what F23 diagnosed and genuinely what the fix resolves.
- A live targeted rerun on `AgML`/`BioSPPy` is the final end-to-end check — see `benchmarks/alembic/runs/2026-07-06_rerun4_f22-f23-verify/`.
**Effort.** Medium-High (touched 4 tool files, ~8 functions, shared across all 5 agents) — implemented and verified via direct source confirmation plus a decisive positive/negative test pair, not just inference.

**2026-07-06 live rerun result: confirmed fixed, with a clean natural reproduction.** `AgML`'s Explorer stage itself genuinely timed out at 900s this run (an unrelated, ordinary slow-repo case — not F19/F20/F21/F22), giving a live F20 cross-check for free: the log correctly shows `STAGE TIMEOUT` with **no** following `[Explorer done]` line, while Environment/Coder/Validator — which really did complete — each got their real `[... done]` line and the pipeline ended with a true `Pipeline complete`. Separately, `BioSPPy` hit a genuine slow debugger call (a `pip install` chain, i.e. exactly F23's scenario) — sent at `10:53:39`, and `[debugger] call timed out after 600s` fired at `11:03:39`, **exactly 600.0s later, to the second**. In the pre-fix rerun3 case, this exact log line never appeared even ~20 minutes after it should have. Both pipelines completed all 4 stages end-to-end this run (vs. rerun3's truncated "validation.md not readable" outcome for both), producing full, real per-tool verdicts. F23 is closed.

### F24 — Validator/debugger handoff has no path for "the sample is wrong," not "the code is wrong," and fixes don't propagate across sibling tools
**Problem.** Found while explaining why `AgML` and `BioSPPy` still ended up FAILED overall in the rerun4 live-verification run (2026-07-06), even though F22/F23 both worked correctly (Validator stage durations were 1787/1800s and 1490/1800s — both finished "naturally," no truncation). Traced every debugger/`invoke_mcp_tool` call in both logs; the pattern is identical and systemic, not a fluke:
- **Sample-size diagnoses have no corrective path.** `instructions/validator.py`'s Step 4 explicitly says: *"The debugger will... itself have re-run `invoke_mcp_tool` to verify its fix. Trust its summary; do NOT call `invoke_mcp_tool` again... unless the debugger reports it could not verify."* This assumes every failure is a **code bug** the debugger can edit and self-verify. For `BioSPPy`'s `quality_ecg`/`eda`/`eeg`, the debugger correctly diagnosed *"a 10-second segment is required, this is not a bug"*, *"sample... too [short]"*, *"only 3 samples"* — but the actual fix is a different `invoke_mcp_tool` argument, which the debugger cannot change (it only edits files). There is no mechanism today for that diagnosis to trigger a corrected retry with a bigger sample — it is marked FAILED and abandoned. This is the same root problem F18 targeted (sample sizing), resurfacing at the validation layer instead of the coder-writes-the-sample layer, and independently confirms F18 is probabilistic, not a hard guarantee: `coder.py`'s instruction was unchanged and still in place this run, but the Coder wrote `[0.1, 0.2, 0.3, 0.4]`-style arrays for `BioSPPy` again anyway.
- **A fix to one tool doesn't propagate to a sibling tool with the identical bug.** The debugger fixed `ecg`'s argv-construction bug (`FileNotFoundError: '--show'`, a boolean flag mishandled as a positional arg) and reported success. `ppg` has the identical bug in its own separate helper file; the validator tested `ppg` fresh afterward and hit the exact same error — but per Step 4's "max 2 debugger calls per tool" framing, each tool is debugged independently, so the shared root cause was never recognized as such.
- **Same pattern in `AgML`:** `train_model_on_dataset`'s debugger fix was never re-verified before the validator moved on to `run_inference_on_dataset`; ditto for `run_inference_on_dataset` → `evaluate_model_on_dataset`. (`AgML`'s underlying bugs — a `KeyError: 'bbox'`, a model-class-count/tensor-reshape mismatch — are separately just genuinely hard, unrelated to this gap; noted for completeness, not part of the fix.)
- **Minor, distinct anomaly noted in passing:** one debugger call (`BioSPPy`/`ppg`) returned a blank `{'result': ''}` after 317s — not a timeout (no "600s" log line), not F17/F22's known JSONDecodeError/finish_reason signatures. Uninvestigated; flag for whoever picks this up.
- **More fundamentally: every "PASSED after debugger fix" verdict the system has ever produced rests entirely on the debugger's own self-report, never independently re-checked by the validator.** This isn't limited to the unhappy paths above — it's Step 4's policy on every single tool, including ones that end up looking like a clean, uneventful pass. Confirmed by re-reading the **2026-06-30 baseline** `AgML` log (found while investigating the 2026-07-06 final-eval timeout, unrelated task): all 5 tools show `— PASSED` in `validation.md`, but for every one of them the validator called `invoke_mcp_tool` exactly **once**, got a failure, delegated to the debugger, and moved straight to the *next* tool the moment the debugger returned its summary — it never re-invoked the fixed tool itself. The "PASSED" label is the debugger's own claim (*"Verification result: tool re-invoke OK"*), asserted from inside a nested agent call the outer validator has no visibility into beyond the text summary. This is by design per Step 4's literal wording, not a bug in any one run — but it means the whole benchmark's pass-rate numbers (this run and all prior ones) are only as trustworthy as the debugger's internal self-checks, with no independent second opinion anywhere in the loop.
**Spec — what a fix needs (deferred, not yet implemented; holding for the post-2026-07-10 backlog per explicit instruction).**
1. Give the debugger a way to signal "the code is correct, the sample/argument is the problem, retry with: `<corrected args>`" as a distinct outcome from "fixed" or "could not verify" — and have the validator's Step 4 act on it (one corrected retry, not unbounded).
2. Track bug fixes by root cause/file, not just by tool name, so a fix to a shared helper pattern (e.g. argv construction shared across `ecg`/`ppg`/`eeg`) is recognized as covering sibling tools before re-testing them independently — or at minimum, re-test a sibling tool that shares a helper-generation pattern after a fix, instead of treating each tool as fully independent.
3. This is squarely adjacent to F1/F4 (deterministic gates) and F3 (held-out validation) already in the optional backlog — likely best designed together with those rather than as a one-off patch.
**Effort.** Medium (validator/debugger protocol change, not a single-file patch) — **explicitly deferred**, same reasoning as F22/F23 pre-fix: not blocking the 2026-07-10 submission, documented here with full evidence so it doesn't need re-diagnosing later.

### F25 — SKIP is a soft LLM convention, not an enforced gate — and there's no tier for genuinely heavy tools

**Problem.** Found while diagnosing the 2026-07-06 final-eval `AgML` validator timeout (see DEMO_READINESS_TODO.md §1a). The Coder correctly identified `train_detector` as too expensive to sample-invoke and wrote `SKIP` for it in `server.md`'s samples block. `instructions/validator.py` Step 4 says *"For every entry... that is NOT marked SKIP: invoke..."* and *"Tools whose sample is SKIP are reported as skipped — not failures."* The validator invoked it anyway, with the tool's own default `epochs=100` (a real Ultralytics YOLO training run), which then consumed most of the 1800s stage budget before hitting an unrelated dataset-export bug. SKIP is parsed and acted on entirely by the validator LLM reading free-text YAML — there is no code-level check anywhere that actually prevents an `invoke_mcp_tool(train_detector, ...)` call from being attempted.

There's a second, related gap: even when SKIP *is* honored, a genuinely heavy tool (real training, real large-dataset processing) then gets **zero** verification, not even a slow one — the two options today are "cheap enough to fit in the shared 1800s budget" or "never checked at all."

**Spec.**
1. **Make SKIP a hard, code-enforced gate, not an LLM-followed convention.** Parse `reports/server.md`'s `samples:` YAML block programmatically (a small, already-structured block) right before the Validator stage starts, and inject the computed SKIP/invoke split explicitly into the validator's opening message as a concrete list ("Do NOT invoke: train_detector. Invoke only: load_dataset, run_inference, evaluate_detection_model, visualize_dataset_samples.") — a system-computed constraint the LLM is directly told is far more reliable than expecting it to correctly self-filter from a markdown block on every run. Belt-and-suspenders option: have `invoke_mcp_tool` itself refuse a call against a tool name found in the parsed SKIP set, returning `{"skipped": true, "reason": "..."}` instead of running it, so enforcement doesn't depend on the LLM at all.
2. **Add an optional, separate "extended validation" pass for SKIP-marked tools, decoupled from the main Validator's shared timeout.** Not a bigger `STAGE_TIMEOUT["validator"]` for everyone (that punishes every repo's normal-weight tools to accommodate the rare heavy one) — instead, a distinct stage/pass that runs *only* against the tools the main pass skipped, with its own, much larger per-tool budget (tens of minutes), run separately (e.g. via the existing `--resume` mechanism, or a dedicated CLI flag / opt-in benchmark pass) so it doesn't inflate the default per-repo wall-clock cost. Failing this pass still doesn't count as harshly as a main-pass failure — it's closer to "verified as far as time allowed."
3. Cheap immediate mitigation, independent of 1–2: for training/inference-style tools specifically, `coder.py`'s sample-invocation rules should require a genuinely cheap parameterization (tiny epoch count, tiny dataset subset) *in addition to* the option to mark SKIP, mirroring what baseline's `AgML` run did successfully (`epochs=2` — validated for real, cheaply, no SKIP needed) — giving the validator a low-cost path to real coverage instead of an all-or-nothing choice between "full-cost real run" and "no run at all."

**Integration.** (1) is a `main.py`/`agents.py` change (parse `server.md`, thread the computed list into the validator's initial prompt and/or `invoke_mcp_tool`'s dispatch). (2) is a new optional stage, analogous to today's 4-stage pipeline. (3) is a `coder.py` instruction addition next to the existing SKIP rules (`instructions/coder.py` lines ~352–385).
**Effort.** (1) Low–Med. (2) Med (new stage/pass, needs a design decision on where it plugs into `run_benchmark.py`). (3) Low.

**Effort.** Low (instruction-only, same class of fix as F18/F21).

### F27 — Tools with too many parameters are a disproportionate failure point

**Problem.** Comparing the same repo's tool surface across 3 independent runs (`aizynthfinder`, `AgML`): runs where the Coder wrapped the repo's existing CLI/API 1:1 with a handful of parameters succeeded (with normal debugging); runs where it invented a broader custom interface — most starkly `aizynthfinder`'s final-eval single `perform_retrosynthesis(smiles, config, policy, stocks, output, nproc, cluster, post_processing, pre_processing, checkpoint)` (10 params covering nearly every internal search-config knob) — failed, partly on a hallucinated import (see F28) but generally correlating with more surface area for something to go wrong. `AgML`'s rerun2 also added an extra `export_to_pytorch_loader` tool not present in the cleaner baseline/final-eval surfaces.
**Spec.** Add explicit guidance to `coder.py` capping tool complexity: prefer tools with a small number of parameters (rule of thumb: ≤4–5) that map to a single, well-defined operation; when a wrapped function exposes many optional configuration knobs, surface only the essential 2–3 as tool parameters and hardcode sensible defaults for the rest internally, rather than mirroring every option as a parameter. As a secondary, measurable enrichment: extend F12's per-run metrics to record parameter counts per generated tool (cheap AST parse of `server.py`'s `@mcp.tool()` signatures in `run_benchmark.py`'s `extract_validation()` or a new step), so "tool complexity vs. failure rate" becomes a tracked, quantified correlation across benchmark runs instead of this session's one-off qualitative observation.
**Integration.** `instructions/coder.py` (tool-design guidance, near Step 3/4). Metric enrichment in `run_benchmark.py`/`agent_runtime.py` (F12 follow-on).
**Effort.** Low (instruction). Low (metric enrichment, optional).

### F28 — `validate_syntax` never checks the helper scripts that contain the actual per-tool logic — extends/concretizes F1

**Problem.** Root-caused while explaining why `aizynthfinder`'s final-eval `expand_molecule` failure (`ImportError: cannot import name 'AiZynthExpander' from 'aizynthfinder'` — a hallucinated class that doesn't exist in the library) wasn't caught by the "Syntax & Imports: PASSED" check before ever reaching a live `invoke_mcp_tool` call. Read `tools/invoke.py`'s `_validate_syntax_sync()`: it `py_compile`s and import-execs **only `server.py`**. The helper scripts under `helpers/*.py` — which contain the actual imports and per-tool logic, and are only ever invoked lazily via `subprocess.run` when a tool is actually called — are never syntax-checked, never import-checked, never touched by this function at all. A hallucinated import/class/function name inside a helper script is therefore invisible until the Validator burns a live invocation attempt (subprocess spin-up, traceback capture) and a full debugger round-trip on something a sub-second static check could have caught for free, in parallel with `server.py`'s own check, before Stage 4 even starts.
**Spec.** Extend `_validate_syntax_sync()` to iterate every file under `helpers/`, and for each: (a) `py_compile` it (catches plain syntax errors), and (b) AST-parse its `Import`/`ImportFrom` nodes and, for each imported name, verify it actually exists on the target module via `importlib.import_module(...)` + `hasattr(...)` inside the server venv — without executing the script's own `main()`/`if __name__ == "__main__":` body (helper scripts are meant to run standalone with argv, so a full `exec_module` isn't safe/meaningful here the way it is for `server.py`). This directly targets the exact failure class found this session (`cannot import name X from Y`) without needing full semantic execution. `coder.py`'s Step 2 ("verify API signatures before writing helpers") should also be extended to explicitly say: grep/read to confirm a class or function **exists** in the target module before importing it, not just that its *parameter names* match — the existing instruction only covers the latter.
**Integration.** `tools/invoke.py`'s `_validate_syntax_sync()` (code). `instructions/coder.py` Step 2, ~line 280–288 (instruction). This is a concrete, low-effort, high-confidence-evidence slice of the long-deferred **F1** (static import/symbol AST gate) — not the full F1 (which also covers `server.py`-level checks and possibly gating tool *selection*, not just post-hoc verification), but the specific gap this session's evidence points at.
**Effort.** Low.

## Out of scope / explicitly not recommended
- **gitingest / DeepWiki external analysis (ToolRosella).** Fragile (rate limits, "Loading…" states, `verify=False`). Alembic's direct file-reading explorer is more robust; treat external knowledge as optional augmentation only.
- **Single-function / task-spec model (ToolMaker).** Do **not** drop autonomous multi-tool discovery — it is alembic's core advantage; borrow ToolMaker's *validation/isolation* mechanisms, not its task-scoped generation model.
