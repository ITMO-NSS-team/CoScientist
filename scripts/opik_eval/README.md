# scripts/opik_eval — оценка надёжности прогонов через Opik

Стенд для эталонного замера текущего пути «одним запросом» (DEVGRAPH: шаг плана R04,
задача F015h). Считает по сохранённым в Opik прогонам три показателя ненадёжности,
которые мы устраняем модулем экспериментов (F015):

- **пустые ответы модели** (флакайность провайдеров OpenRouter);
- **обращения к незарегистрированным инструментам** («Tool 'X' not found»);
- **разгон цикла оркестратора** (число вызовов модели / упор в потолок времени).

## Запуск

```bash
.venv/bin/python scripts/opik_eval/run_baseline.py --limit 24
```

- Учётные данные берутся без импорта пакета CoScientist: переменные окружения
  `OPIK_API_KEY`, иначе `~/.opik.config`, иначе `.env` (`OPIK__API_KEY`).
- Результат печатается в консоль и сохраняется в `results/baseline_<дата>.md` и `.json`.
- `--limit N` — сколько последних прогонов взять; `--sleep S` — пауза между запросами
  (Opik ограничивает частоту поиска по спанам; при превышении стенд сам ждёт и повторяет).

## Файлы

- `opik_client.py` — получение учётных данных и клиента Opik.
- `metrics.py` — показатели по одному прогону (`trace_metrics`) + повтор при ответе 429.
  Порог разгона: `RUNAWAY_LLM_CALLS=25` или `RUNAWAY_SECONDS=690`.
- `run_baseline.py` — сводка по моделям + худшие разгоны + список «ненайденных»
  инструментов и типов ошибок.

## Важно про эталон

Окно «последние N прогонов» смешивает рабочие задачи с отладочными — это **снимок**,
а не контролируемый замер. Для приёмки (шаг R19) нужен чистый прогон фиксированного
набора задач из `dataset_S.xlsx` на одной модели с записью логов в файл. Крайние случаи
разгона (до 81 вызова, F014.A1) лежат в более старых прогонах — увеличьте `--limit`
или добавьте фильтр по дате, чтобы их захватить.
